# 01 / Motivation

## 【R】Open


**▶ 镜头 005｜【R】开场，直接对镜头**  `素材：R-001`

最初开始 Odyssey 这个项目，其实是因为在接触不同的 AI Agent 工具时，产生了一些疑问。


**▶ 镜头 007｜【R+M】Claude Code / Codex 图标轻量叠加；无需专门动画**  `素材：R-002 + GFX-001`

一方面，像 Claude Code、Codex 这样的自主 Agent，已经能够独立完成越来越复杂的任务。

> 依次出现 Claude Code, Codex 图标辅助说明（应该不违反版权吧……？）


**▶ 镜头 011｜【R+M】真人小窗 + Agent 行为抽象 Motion（新增 M-08，选做）**  `素材：R-003 + M-08`

但与此同时，我们也在逐渐失去对它们内部决策过程的直接控制。

我们可以给它们目标，查看执行记录，也可以在必要的时候进行干预。但很多时候，我们并不知道它们接下来究竟会采取什么行动，又为什么会作出这样的选择。

> 【M】录制一段 AI 生成文字视频？或者制作一个 motion 表达 Agent 完成任务？—— 真人出镜在左上角/右下角。


**▶ 镜头 017｜【R】提出系统结构问题**  `素材：R-004`

这让我开始思考：当一个 Agent 系统需要长期运行，或者需要多个 Agent 相互协作时，我们是否仍然需要一种更加明确、更加容易理解的系统结构？


**▶ 镜头 019｜【R+M】Coze / Dify / Bedrock 图标叠加**  `素材：R-005 + GFX-002`

另一方面，我也了解了一些现有的 Agent 编排平台，比如 Coze、Dify 和 Amazon Bedrock。

> 依次出现 Coze，Dify，Amazon Bedrock 这些图标（剪辑软件可以完成）。


**▶ 镜头 023｜【M｜录屏】Dify 现有产品界面演示，非新 Motion**  `素材：SCR-001`

这些工具已经提供了相当丰富的功能。我们可以设计 Workflow，配置 Agent，连接各种外部工具，构建复杂的自动化系统。

>录制一段 Dify 的使用视频（拖动节点到画布即可）


**▶ 镜头 027｜【R】对工具复杂度的观察与反思**  `素材：R-006`

但我逐渐发现，功能丰富并不一定意味着系统容易理解。

随着功能不断增加，节点类型、配置选项和抽象概念也变得越来越多。

有时候，真正让我感到困难的，并不是某一个功能如何实现，而是这些功能为什么要以这样的方式组织在一起。


**▶ 镜头 033｜【R】提出 Odyssey 的核心追问**  `素材：R-007`

于是我开始想：

如果我们不急着增加新的功能，而是重新思考这些功能之间的关系，会怎么样？

有没有可能用一套更加统一的概念，让复杂的 Agent 系统变得更容易理解、设计和维护？


**▶ 镜头 039｜【R】项目缘起与名称**  `素材：R-008`

这就是 Odyssey 最初的出发点。

至于为什么叫 Odyssey——


**▶ 镜头 043｜【R】奥德修斯故事和个人设计理念；可选静态插画/文字，不必新建 Motion**  `素材：R-009`

我一直很喜欢奥德修斯的故事。

而且我也逐渐形成了一种看法：复杂的系统往往很难在一开始就被完整地设计出来。

所以，我希望 Odyssey 不只是一个预先定义好所有功能的软件，而是一个能够在探索、实践和修正中逐渐形成的系统。

# 02 / Start — From Ideas to Concepts


**▶ 镜头 059｜【R】章节开场**  `素材：R-011`

Odyssey 最初的设计，其实是从几个很简单的问题开始的。


**▶ 镜头 061｜【M｜文字卡】原稿已有黑底白字提示**  `素材：TXT-001`

【M】黑底白字，就下面一句话。


**▶ 镜头 063｜【M｜文字卡】第一个核心问题，延续前一文字卡**  `素材：TXT-002`

第一个问题是：我们应该怎样理解一个 Agent 系统的整体结构？

【M】


**▶ 镜头 067｜【R+M】简化的配置分散示意；可用草图，不强制新 Motion**  `素材：R-012 + GFX-003`

通常，当我们设计 Agent Workflow 时，注意力会集中在执行流程上。但一个完整的 Agent 系统，除了 Workflow，还包含大量其他配置，比如 Settings、Guardrails，以及不同 Agent 之间的协作关系。

如果这些信息散落在不同的页面和配置项里，我们就很难直观地理解整个系统。


**▶ 镜头 071｜【M｜草图】SK-01，建议与接下来 M-01 连续**  `素材：M-01`

**[SK-01 · Pattern]**


**▶ 镜头 073｜【M｜新 Motion】M-01：Execution Module × Execution Behavior；包含二维关系和配置填充**  `素材：M-01`

所以，我最早的一个想法，是尝试用二维的矩形结构，把这些配置组织起来。

横向表示不同的 Execution Module，每个 Execution Module 中用 Pattern——实际上就是拓扑结构，将不同的 agent 串起来；纵向表示 Execution Behavior，表示贯穿系统执行的行为。Execution Module 和 Execution Behavior 的区别在于Execution Module (Pattern) - 主动推进系统状态；而Execution Behavior - 不主动推进系统状态。

**[M-01 · Execution Module × Execution Behavior]**

在二维的矩形结构中已经完成配置的部分，用实心颜色填充。


**▶ 镜头 081｜【M｜Figma】UI-05 System Canvas Draft**  `素材：FIG-001`

**[UI-05 · Journey / System Canvas Draft]**

这样一来，我们就可以从整体上看到系统的组成，以及各个部分的配置状态。


**▶ 镜头 085｜【R】Pattern 概念小结、转向 Workflow**  `素材：R-013`

Pattern 这一概念的设计是被用来表达不同 Agent 之间的协作关系。

不过，系统的整体结构只是第一个问题。

接下来，我开始思考 Workflow 本身应该如何设计。


**▶ 镜头 091｜【R+M】现有工具节点示例或草图，保持画面简单**  `素材：R-014 + GFX-004`

现有的一些 Agent 编排工具提供了很多不同类型的 Node。它们能够完成丰富的操作，但也意味着用户需要理解更多的概念。

我开始想，是否有可能减少 Node 的类型，把一些复杂性转移到更底层的 Tool 中？


**▶ 镜头 095｜【M｜草图】SK-05**  `素材：SK-001`

**[SK-05 · Workflow & Agent Actions]**


**▶ 镜头 097｜【M｜新 Motion】M-02 Workflow Node Taxonomy**  `素材：M-02`

于是，我尝试把 Workflow 中的 Node 分成两类。

一类是 Logic Node，比如 Branch 和 Loop，用来控制执行逻辑。

另一类是 Action Node，负责实际的任务执行。

而 Action Node 又可以进一步分成 Agent Node 和 Task Node。

**[M-02 · Workflow Node Taxonomy]**


**▶ 镜头 107｜【R+M｜新 Motion】M-03 Thinking Ownership: Agent vs Task，真人可小窗**  `素材：R-015 + M-03`

它们最重要的区别，在于 Thinking Ownership，也就是谁负责作出决策。

Agent Node 拥有一定的自主决策空间，可以根据目标决定如何行动。

Task Node 则更接近一次明确的工具调用，按照预先定义的操作执行任务。

**[M-03 · Thinking Ownership: Agent vs Task]**


**▶ 镜头 115｜【M｜Figma】UI-08 Workflow Focus Mode**  `素材：FIG-002`

这种区分也意味着，LLM 不一定需要始终作为一种独立的顶层 Node。

如果我们只是希望调用一次语言模型，那么它也可以作为 Tool，被其他节点调用。

**[UI-08 · Workflow / Focus Mode]**


**▶ 镜头 121｜【R】引出 Agent 的四项配置**  `素材：R-016`

在此基础上，我又开始思考：一个 Agent Node 究竟需要哪些核心配置？

最后，我尝试把它收敛为四个部分：


**▶ 镜头 125｜【M｜草图】SK-06**  `素材：SK-002`

Model、Goal、Knowledge Space，以及 ToolBox。

**[SK-06 · Agent Node / Early Design]**


**▶ 镜头 129｜【M｜新 Motion】M-04 Knowledge Space × ToolBox**  `素材：M-04`

其中，Knowledge Space 和 ToolBox 是我最希望明确区分的两个概念。

Knowledge Space 用来组织 Agent 所依赖的知识、指令和其他文本资源。

ToolBox 则组织 Agent 可以使用的工具，以及它能够执行的操作。

简单来说，一个是认知空间，一个是行动空间。

**[M-04 · Agent: Knowledge Space × ToolBox]**


**▶ 镜头 139｜【R】引出知识组织问题**  `素材：R-017`

但是，当我开始设计 Knowledge Space 时，又遇到了一个新的问题。

如果我们只是把知识存储成一个个独立的文档，那么文档之间的关系应该如何表达？


**▶ 镜头 143｜【R+M】文件夹与引用关系的静态示意，可合并到 M-05**  `素材：R-018 + M-05`

传统的文件夹结构很适合存储和管理文件，但知识之间的关系并不总是层级式的。

一份文档可能同时引用多份其他文档，不同文档之间也可能存在循环引用。


**▶ 镜头 147｜【M｜草图】SK-08**  `素材：SK-003`

**[SK-08 · Knowledge Graph / Early Exploration]**


**▶ 镜头 149｜【M｜新 Motion】M-05 Folder Structure → Knowledge Graph**  `素材：M-05`

所以，我尝试把知识的存储方式和组织方式分开。

文档本身仍然可以保存在传统的文件夹结构中，但文档之间的引用和关联关系，则通过一个有向图来表达。

在这个图中，每个 Node 代表一份文档，Edge 则代表文档之间的关系。

我们还可以通过 Group 和 Tag 来组织相关的知识集合。

**[M-05 · Folder Structure → Knowledge Graph]**

这样，知识就不再只是文件夹中的一个个独立文件，而是可以被组织成一个相互关联的网络。


**▶ 镜头 161｜【M｜Figma】UI-17 Knowledge Space Graph Overview**  `素材：FIG-003`

**[UI-17 · Knowledge Space / Graph Overview]**


**▶ 镜头 163｜【R+M｜新 Motion】M-06 Retrieval vs Graph Navigation，避免声称已实现**  `素材：R-019 + M-06`

这也让我开始重新思考知识检索的问题。

像 RAG 这样的检索方法，可以帮助我们快速找到与问题相关的信息。但如果只是依赖局部文本片段，我们未必能够充分理解这些信息之间的结构关系。

所以，我希望 Odyssey 能够探索另一种方式：让 Agent 不仅可以检索相关内容，也可以沿着知识之间的关联进行导航。

当然，这并不意味着要放弃 RAG。

在 Odyssey 的设计中，RAG 仍然可以作为一种 Tool，与知识图的导航能力相互补充。

**[M-06 · Retrieval vs Graph Navigation]**


**▶ 镜头 175｜【R】对独立设计想法的回望**  `素材：R-020`

回过头来看，这些想法最初其实是相对独立的。

有些来自对 Workflow 的思考，有些来自对 Agent 配置的简化，还有一些来自知识组织的问题。

但慢慢地，我发现它们其实指向了同一个目标。

我希望一个复杂的 Agent 系统，不只是拥有越来越多的功能，而是能够通过一套相对统一的概念，把这些功能组织起来。


**▶ 镜头 183｜【M｜新 Motion】M-07 Four Core Concepts**  `素材：M-07`

Pattern 用来表达协作关系。

Workflow 用来组织执行逻辑。

Knowledge Space 用来管理认知资源。

ToolBox 用来组织行动能力。

**[M-07 · Four Core Concepts]**


**▶ 镜头 193｜【R】承认复杂性并过渡到界面设计**  `素材：R-021`

这当然不意味着复杂性会消失。

但至少，我们可以尝试让复杂性以一种更加清晰、更加容易理解的方式呈现出来。

而到了这一步，这些想法仍然只是一些草图和概念。

接下来的问题是：怎样才能把它们变成真正可以使用的界面？

# 03 / Figma — From Concepts to Interfaces


**▶ 镜头 206｜【R】Section 03 开场，讲学习经历**  `素材：R-022`

在有了这些初步的设计想法之后，我开始尝试把它们转化为真正的用户界面。

但这里出现了一个新的问题。

我之前其实并没有太多使用 Figma 进行 UI 设计的经验。

最开始的时候，我甚至不太清楚应该怎样把那些抽象的概念，组织成一个可以实际操作的界面。

不过后来我意识到，我并不需要先成为一个专业的 UI Designer。

至少在这个阶段，我真正需要的，是一种能够把设计想法具体表达出来，并且可以不断修改和验证的方式。


**▶ 镜头 218｜【M｜Figma】早期草图与 Figma 设计稿切换；已有素材**  `素材：FIG-004`

于是，我开始一边学习 Figma，一边尝试设计 Odyssey 的界面。

这个过程其实和最初画草图很不一样。

在草图里，我可以很自由地定义概念，以及它们之间的关系。


**▶ 镜头 224｜【R+M｜Figma】展示 UI 层级、配置面板和页面导航；不需要新 Motion**  `素材：R-023 + FIG-005`

但当这些概念真正进入界面时，我就必须开始考虑一些更加具体的问题。

比如，用户应该从哪里进入一个 Agent？

不同层级的信息应该怎样组织？

哪些配置应该直接展示，哪些又应该放进更详细的页面？

还有，用户应该怎样在 Workflow、Agent 配置和 Knowledge Space 之间切换？


**▶ 镜头 234｜【R】界面设计反过来影响概念设计**  `素材：R-024`

这些问题并不只是视觉设计的问题。

它们实际上也在迫使我重新审视之前的概念设计。


**▶ 镜头 238｜【R+M｜Figma】Pattern 原方案与收敛方案对比；可用静态卡片**  `素材：R-025 + FIG-006`

其中一个例子，就是 Pattern 的设计。

最初，我希望用户能够自由定义不同 Agent 之间的拓扑结构。

但随着设计逐渐具体化，我发现这种自由度也会带来非常高的配置复杂度。


**▶ 镜头 244｜【M｜新 Motion】Pattern 从任意拓扑收敛为 Linear / Solo / Hub and Spoke / Circle（新增 M-09，推荐）**  `素材：M-09`

所以后来，我决定收敛这个设计。

不再要求用户自己定义任意拓扑，而是由系统提供几种预先定义的 Pattern，比如 Linear、Solo、Hub and Spoke，以及 Circle。

这意味着用户失去了一部分自由度，但整个系统也因此变得更加容易理解和配置。


**▶ 镜头 250｜【R】总结设计取舍**  `素材：R-026`

对我来说，这也是设计过程中一个很有意思的发现。

有时候，好的设计并不意味着提供尽可能多的选择，而是决定哪些选择真正有必要留给用户。


**▶ 镜头 254｜【M｜Figma】Workflow Canvas / 配置面板展示**  `素材：FIG-007`

类似的问题也出现在其他界面的设计中。

比如，Workflow 不只是需要一张能够展示执行逻辑的 Canvas。

用户还需要在不同的层级之间移动，查看节点的具体配置，并且理解当前正在编辑的是哪一部分。


**▶ 镜头 260｜【M｜Figma】Knowledge Space 文档管理与图谱页面**  `素材：FIG-008`

同样，Knowledge Space 也不只是需要一张知识关系图。

用户还需要管理文档、查看文档内容，以及理解这些文档和整个知识结构之间的关系。


**▶ 镜头 264｜【R】Figma 是思考工具，不仅是绘图工具**  `素材：R-027`

这些看起来很具体的交互问题，反过来又影响了我对系统结构的理解。

所以，Figma 对我来说，并不只是一个把界面画得更漂亮的工具。

它也逐渐成为了一个帮助我思考和修正设计的地方。


**▶ 镜头 270｜【R+M｜Figma】迭代过程可用界面前后对比**  `素材：R-028 + FIG-009`

当然，这些界面并不是一次就设计完成的。

很多时候，我只是先做出一个能够表达想法的版本，再根据遇到的问题不断调整。


**▶ 镜头 274｜【R】提问并过渡到代码**  `素材：R-029`

而当 Odyssey 的界面开始慢慢成形之后，下一个问题也就出现了。

这些设计，能不能真正运行起来？

# 04 / Vibe Coding


**▶ 镜头 280｜【R】Section 04 开场：Vibe Coding**  `素材：R-030`

在完成初步的 Figma 设计之后，我开始尝试把这些界面真正实现出来。

这一次，我主要使用 AI 辅助编程。

对我来说，这其实是一种很有意思的开发方式。


**▶ 镜头 286｜【R+M｜录屏】真实开发环境、编辑器或代码片段，勿伪造实现过程**  `素材：R-031 + SCR-002`

我可以把更多精力放在系统应该如何工作、不同部分应该怎样组织，以及用户究竟需要什么样的交互上。

而具体的代码实现，则可以借助 AI 来完成。


**▶ 镜头 290｜【R】澄清 AI 辅助编程不等于自动完成**  `素材：R-032`

当然，这并不意味着我只需要描述一个想法，剩下的事情就会自动发生。


**▶ 镜头 292｜【R+M｜录屏】结合真实代码/配置展示设计问题**  `素材：R-033 + SCR-003`

很多时候，真正困难的部分，是发现自己原本的设计还不够明确。

当一个概念只存在于设计稿中时，我可以暂时忽略一些细节。

但当它需要变成真正的软件时，我就必须开始回答更加具体的问题。


**▶ 镜头 298｜【M｜录屏】节点数据、Agent/Task 配置、Tool 输入输出和 Canvas 配置；已有软件录屏**  `素材：SCR-004`

比如，不同节点之间应该怎样传递数据？

Agent 和 Task 应该如何划分各自的职责？

Tool 的输入和输出应该怎样定义？

以及，用户在 Canvas 中做出的配置，应该如何转化为系统能够理解的数据结构？


**▶ 镜头 306｜【R】设计与实现相互修正的反思**  `素材：R-034`

这些问题让我逐渐意识到，从界面设计到软件实现，并不是一个简单的翻译过程。

它也是一个不断补充和修正设计的过程。


**▶ 镜头 310｜【R+M｜录屏】引出 Document Curator，切换到完整 Canvas**  `素材：R-035 + SCR-005`

随着 Odyssey 的编辑器逐渐成形，我决定尝试设计第一个相对完整的业务案例。

我把它叫作 Document Curator。


**▶ 镜头 314｜【M｜录屏】Document Curator 业务场景和整体 Workflow；可添加简单标注**  `素材：SCR-006`

这个案例的目标，是帮助维护一个 Knowledge Space 中的文档和知识关系。

比如，当一份文档发生变化时，系统需要理解修改后的内容，检查相关文档，并判断是否需要更新摘要、标签，或者文档之间的关系。


**▶ 镜头 318｜【R】解释为何不能让 AI 自行决定所有修改**  `素材：R-036`

但这里有一个问题。

这些修改并不总是能够直接交给 AI 来决定。

有些修改可能很明确，可以自动处理。

但另一些修改可能涉及不确定的信息、相互矛盾的证据，或者需要人工确认的知识关系。


**▶ 镜头 326｜【M｜录屏】展示 Solo Pattern 和完整 Workflow**  `素材：SCR-007`

所以，我希望设计一个 Workflow，让 AI 负责提出建议，而不是直接决定所有修改。

在 Odyssey 中，我使用了一个 Solo Pattern。

也就是说，这个案例只需要一个 Agent，而不涉及多个 Agent 之间的协作。


**▶ 镜头 332｜【M｜录屏】依次聚焦 Read Document Context → Agent Action → Proposal**  `素材：SCR-008`

整个 Workflow 从一个 Task 开始。

它首先读取发生变化的文档，以及与这次修改相关的上下文和规则。

然后，流程进入一个 Agent Action。

这个 Agent 配置了自己的 Model 和 Goal，也可以访问 Knowledge Space，并通过 Toolbox 检索相关文档。

在这个步骤中，Agent 的任务不是直接修改知识库。

它需要根据已有的文档、规则和检索到的证据，提出一组具体的修改建议。

比如，哪些元数据需要更新，哪些文档关系需要增加，以及这些建议分别依据什么信息。


**▶ 镜头 346｜【M｜录屏】聚焦 Validate Proposal Task 和校验配置**  `素材：SCR-009`

接下来，Workflow 会进入另一个 Task。

这一步负责验证 Agent 提出的建议。

它需要检查数据结构是否正确、修改是否有足够的证据，以及这些操作是否符合预先定义的规则。


**▶ 镜头 352｜【R+M｜录屏】强调 Agent 提案与独立验证的权限边界**  `素材：R-037 + SCR-010`

我特意把这个步骤和 Agent Action 分开。

因为我不希望 AI 在提出修改建议的同时，还能够自行决定这些建议是否应该被批准。


**▶ 镜头 356｜【M｜录屏】聚焦 Branch 与 Apply / Review 两条路径；静态高亮即可**  `素材：SCR-011`

随后，一个 Branch 会根据验证结果，决定 Workflow 应该进入哪一条路径。

如果修改符合自动处理的条件，就进入 Apply Validated Changes。

如果需要进一步确认，就进入 Save Review Proposal，把建议保留下来，等待人工审核。


**▶ 镜头 362｜【R+M｜录屏】回看完整 Canvas，归纳各节点职责**  `素材：R-038 + SCR-012`

这样，一个完整的业务流程就被组织成了几个不同的部分。

Agent Action 负责需要理解和判断的工作。

Task 负责更加明确、可以按照规则执行的操作。

Branch 则负责根据条件控制流程。

而 Knowledge Space、ToolBox 和变量系统，为这些步骤提供所需的信息与数据连接。


**▶ 镜头 372｜【R】案例设计的意义**  `素材：R-039`

对我来说，这个案例最有意思的地方，是这些原本分散在设计文档中的概念，终于开始出现在同一个 Workflow 里。

它们不再只是一些单独的功能或者界面。

我开始能够用它们描述一个具体的业务问题，以及系统应该如何处理这个问题。


**▶ 镜头 378｜【M｜录屏】Canvas ↔ DSL 双向表达展示；只演示已验证功能**  `素材：SCR-013`

除了可视化 Canvas，我还为 Odyssey 设计了一套 Domain-Specific Language，也就是 DSL。

这意味着，同一个 Workflow 不仅可以通过图形界面进行配置，也可以通过文本来描述和编辑。

这两种表达方式可以相互转换，让用户根据自己的习惯，选择更加直观的可视化操作，或者更加精确的文本配置。


**▶ 镜头 384｜【R】明确案例是设计与配置验证，不是实际执行**  `素材：R-040`

不过，Document Curator 目前仍然是一个设计与配置案例。

虽然我已经能够在编辑器中组织这个 Workflow，并验证它的配置表达，但真正的执行引擎、外部服务接口，以及 Agent 输出与后续步骤之间的连接，还有很多工作需要完成。

所以，这个案例并没有证明 Odyssey 已经能够完整运行。


**▶ 镜头 390｜【R+M｜录屏】回看 Canvas 或设计细节，收束案例**  `素材：R-041 + SCR-014`

它更像是一次初步的检验。

我终于可以把之前提出的概念放进一个具体的场景里，看看它们是否能够组成一个相对清晰、一致的系统。

与此同时，这个过程也让我发现了许多之前没有充分考虑的问题。

而这些问题，可能正是 Odyssey 接下来需要继续解决的事情。

**▶ 镜头 414｜【R】项目边界与创作定位**  `素材：R-045`

当然，它仍然有很多不完善的地方。

但我并不急着把它变成一个完整的商业产品。


**▶ 镜头 418｜【R】开放式探索与个人感受**  `素材：R-046`

对我来说，Odyssey 更像是一次持续进行的探索。

**▶ 镜头 422｜【R+M｜蒙太奇】项目素材缓慢淡出，可选**  `素材：R-047 + EDIT-002`

**▶ 镜头 424｜【R】结尾直视镜头，留出停顿**  `素材：R-048`

我还不知道最后会发生什么。

而这段旅程，还没有结束。
