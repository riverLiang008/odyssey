# Odyssey M2.3 Pattern Domain Strategies 与 Commands Implementation Plan

> Status: Implementation complete; pending independent acceptance  
> Milestone: M2.3  
> Scope: 纯 TypeScript Pattern domain rules、strategies、commands 与 invariant tests  
> Prerequisite: M2.1 accepted; M2.2 accepted  
> Figma reference: [`OdyJourney — Pattern Templates` (`300:33`)](https://www.figma.com/design/P3EF9io2DhyhwkNYBVqB5Z/Odyssey-Design?node-id=300-33)  
> Authoritative guideline: [`frontend-engineering-guidelines.md`](../../frontend-engineering-guidelines.md)

## 1. 目标与完成结果

M2.3 在不依赖 Vue、Pinia、DOM、drag event 或 Vue Flow 的前提下，实现四种 V1 built-in Pattern 的权威领域规则：

```text
Pattern template key
→ strategy.instantiate(idFactory)
→ valid PatternConfig
→ command(intent, PatternConfig)
→ new PatternConfig | PatternDomainError
→ strategy-derived routes and presentation layout
```

完成后，M2.4 的 System Canvas 和 DnD 只需要：

- 把 UI event 转换为 typed intent；
- 调用 M2.3 command；
- 展示 command result/error；
- 使用派生 layout 渲染 Slots/Routes。

UI 不再自行判断 topology、修改 slots、计算 routes 或决定 move/exchange/reorder 语义。

## 2. 权威边界与资料结论

### 2.1 已冻结 contract

M2.3 必须直接使用 `@odyssey/schemas` 中的：

- `PatternKind` / `PatternTemplateKey`；
- `PatternConfig`；
- `PatternSlot`；
- `PatternRoute` / `PatternRouteTarget`；
- branded `UUID`。

持久化规则已确定：

- schema version 为 `1.0.0`；
- built-in kinds 为 `hub_and_spoke | diamond_loop | linear_sequence | solo_component`；
- `templateKey` 只记录 provenance，`kind` 决定当前 topology rule；
- Slots 和 Routes 显式持久化；
- route 只引用 slot UUID；
- built-in Slot 坐标不持久化；
- 用户不直接创建、删除或绘制 Pattern Routes；
- `PatternConfig` 实例化后是唯一事实源，不依赖 template card 或 Figma layer。

### 2.2 Figma 能提供与不能提供的内容

Figma `300:33` 展示四张 built-in template card：

| Pattern | Figma 描述 | 可用于 M2.3 |
| --- | --- | --- |
| Hub & spoke | `1 center · 4 routes` | 初始 topology 和 layout 视觉意图 |
| Diamond loop | `4 connected stages` | 四角色 diamond 的视觉意图 |
| Linear sequence | `4 serial stages` | 有序相邻连接和横向布局意图 |
| Solo component | `1 isolated slot` | 单 Slot、无内部 route |

Figma 不是领域 contract。节点像素坐标、card preview 中的线条方向和示例 Agent assignment 不能直接成为持久化规则或业务 identity。

## 3. 开始编码前的决策 Gate

> Decision status: Accepted by product owner on 2026-08-12. The recommended defaults below are the M2.3 implementation baseline.

M2.3 的主风险不是 TypeScript 实现，而是把未冻结的 topology 细节固化成错误规则。Step 1 必须先形成一份小型 accepted topology specification，至少确定：

| 项目 | 必须冻结的内容 | 当前资料状态 |
| --- | --- | --- |
| Hub roles | role 名称、恰好一个 hub、spoke 最小/最大数量 | 只有概念和 Figma `1 center · 4 routes` |
| Hub routes | `hub → spoke`、`spoke → hub` 或双向；是否需要 `journey_end` | 未完全定义 |
| Diamond roles | 四个默认 role 的稳定名称与允许增删的位置 | 只有“4 connected stages”和 diamond 视觉 |
| Diamond routes | 有向边顺序、汇合/回路语义、`journey_end` 来源 | 未完全定义 |
| Linear minimum | 是否允许 0 Slot；删除到 1 Slot时是否仍生成 `journey_end` | canonical 示例只覆盖 2 Slots |
| Route identity | topology 重算时保留可匹配 route ID，还是全部生成新 UUID | 未完全定义 |
| Agent duplication | clone ownership 范围和 transaction boundary | Journey document 只有 Agent summary，完整 aggregate 在独立 Agent document |

推荐默认决策：

1. Solo 固定恰好一个 `solo` role Slot，routes 为空。
2. Linear 至少一个 Slot，每个 Slot `order` 连续为 `0..n-1`；相邻 Slot 生成 route，最后 Slot 生成 `journey_end`。
3. Hub 初始为一个 `hub` + 四个 `spoke`；允许增删 spoke，但不允许删除/复制 hub。
4. Diamond V1 固定四个 roles，不在 M2.3 支持 Slot add/remove；先支持 assignment/move/exchange，避免在规则未定义时发明“permitted positions”。
5. 路由重算使用 semantic endpoint pair 匹配并保留仍存在 route 的 ID；只为新增 route 生成 UUID，删除失效 route。
6. M2.3 的 `duplicateAgent` 分成两个纯边界：先验证 Pattern target/生成 duplication intent；由拥有 Agent aggregate 的 application command 深克隆 Agent 及 owned descendants，再用新 Agent ID 原子提交新 Journey/Agent documents。不得仅复制 Agent summary 或复用 owned IDs。

上述默认值已被接受。Step 1 负责把它们转换为精确、可测试的 specification 和 error catalog，不再等待额外产品决策。

当前没有其他实施 blocker。`duplicateAgent` 的纯 aggregate result 可以在 M2.3 完成，但当前 repository 没有跨 Journey/Agent aggregate transaction；M2.3 不会把多个现有 save 调用包装成伪原子操作。真实持久化 transaction 留给后续 API integration，并在 M2.3 handoff 中明确记录。

### 3.1 Accepted code-level topology specification

| Kind | Slots / roles | Authoritative routes | M2.3 structural operations |
| --- | --- | --- | --- |
| `solo_component` | exactly one `solo`; `order = null` | none | assignment operations only |
| `linear_sequence` | at least one Slot; role is `null`; continuous `order = 0..n-1` | each Slot points to its successor; final Slot points to `journey_end` | add/remove/reorder plus assignment operations |
| `hub_and_spoke` | exactly one `hub` and at least one `spoke`; orders are `null`; template starts with four spokes | one directed `hub -> spoke` route per spoke; no implicit `journey_end` | add/remove spoke plus assignment operations; hub is immutable |
| `diamond_loop` | exactly one each of `entry`, `upper_branch`, `exit`, `lower_branch`; orders are `null` | directed cycle `entry -> upper_branch -> exit -> lower_branch -> entry`; no implicit `journey_end` | assignment operations only |

Routes are compared as semantic endpoint pairs independent of array order. Reconciliation preserves the UUID of surviving pairs, removes obsolete routes, and creates UUIDs only for new pairs. Presentation coordinates are derived and never enter `PatternConfig`.

The Step 1 validation catalog is frozen as `SCHEMA_INVALID`, `PATTERN_KIND_MISMATCH`, `SLOT_CARDINALITY_INVALID`, `TOPOLOGY_ROLE_INVALID`, `SLOT_ORDER_INVALID`, `OWNED_ID_COLLISION`, `AGENT_ASSIGNED_MORE_THAN_ONCE`, and `ROUTE_TOPOLOGY_INVALID`. Command-specific errors are frozen in Step 4 and must reuse this validator.

The accepted Step 4 command-error catalog is: `INVALID_TOPOLOGY`, `SLOT_NOT_FOUND`, `AGENT_ALREADY_ASSIGNED`, `TARGET_SLOT_OCCUPIED`, `SOURCE_SLOT_EMPTY`, `SAME_SLOT`, `OPERATION_NOT_SUPPORTED`, `CARDINALITY_VIOLATION`, `IMMUTABLE_TOPOLOGY_ROLE`, `SLOT_OCCUPIED`, `INVALID_REORDER_POSITION`, and `INVALID_SLOT_LABEL`. These are domain codes only; UI copy remains outside the domain layer.

## 4. 范围

### 4.1 必须完成

- topology specification 和 stable error catalog；
- deterministic/injectable UUID factory；
- 四种 built-in Pattern definitions/template data；
- strategy registry；
- template instantiation；
- Pattern validation；
- route derivation；

- duplicate 的 validation/intent boundary 和 full aggregate remap helper；
- command immutability 与 invariant tests；
- Journey store 的薄 action 接入，但不接 UI/DnD。

### 4.2 明确不做

- Pattern template Vue components；
- HTML5 DnD、PointerEvent 或 drag payload serialization；
- System Canvas、AgentSlot、context menu；
- Vue Flow；

- repository save/autosave orchestration；
- Pattern replacement confirmation UI；
- workflow preview 或 Agent Workflow navigation；
- 后端 Pattern validator。

## 5. 建议代码结构

```text
apps/web/src/domain/pattern/
├── patternDefinitions.ts       # built-in template definitions
├── patternErrors.ts            # stable discriminated error union
├── patternIdFactory.ts         # UUID generation port
├── patternValidation.ts        # aggregate/topology invariants
├── patternRoutes.ts            # semantic route derivation + ID reconciliation
├── patternLayout.ts            # non-persisted presentation layout
├── patternStrategies.ts        # registry and per-kind strategy dispatch
├── patternCommands.ts          # pure command entry points
├── agentDuplication.ts         # explicit aggregate clone/remap helper
└── *.test.ts
```

依赖方向：

```text
@odyssey/schemas
       ↓
domain/pattern pure functions
       ↓
journeyEditor store actions (thin orchestration)
       ↓
M2.4 components / DnD
```

`domain/pattern` 不得导入 `vue`、`pinia`、`vue-router`、`naive-ui`、DOM 或 repository。

## 6. 核心类型设计

### 6.1 Result 与错误

所有可拒绝 command 返回 discriminated result，不抛出预期领域错误：

```ts
type PatternCommandResult<T> =
  | { ok: true; value: T }
  | { ok: false; error: PatternDomainError }

type PatternDomainError =
  | { code: 'PATTERN_KIND_MISMATCH' }
  | { code: 'INVALID_TOPOLOGY'; reason: PatternTopologyErrorCode }
  | { code: 'SLOT_NOT_FOUND'; slotId: UUID }
  | { code: 'AGENT_NOT_FOUND'; agentId: UUID }
  | { code: 'AGENT_ALREADY_ASSIGNED'; agentId: UUID; slotId: UUID }
  | { code: 'TARGET_SLOT_OCCUPIED'; slotId: UUID }
  | { code: 'OPERATION_NOT_SUPPORTED'; operation: PatternOperation; kind: PatternKind }
  | { code: 'CARDINALITY_VIOLATION'; kind: PatternKind }
  | { code: 'IMMUTABLE_TOPOLOGY_ROLE'; slotId: UUID }
```

最终 code 集合在 Step 1 冻结。Domain error 不包含最终 UI 文案。

### 6.2 ID generation

纯函数不能隐式调用全局随机源。实例化、add Slot、route reconciliation 和 duplication 显式接收：

```ts
interface PatternIdFactory {
  patternId(): UUID
  slotId(): UUID
  routeId(): UUID
  agentId(): UUID
  workflowNodeId(): UUID
  workflowEdgeId(): UUID
  variableId(): UUID
  toolId(): UUID
}
```

生产 adapter 可以使用 `crypto.randomUUID()` 后经 UUID runtime validation；测试使用 deterministic sequence factory。若 duplication 还涉及更多 owned identity，应使用按实体区分的 factory method，而不是通用字符串生成器。

### 6.3 Presentation layout

M2.3 layout 是派生 view model，不属于 `PatternConfig`：

```ts
interface PatternPresentation {
  slots: Array<{ slotId: UUID; x: number; y: number }>
  routes: Array<{ routeId: UUID; sourceSlotId: UUID; targetSlotId: UUID | null }>
}
```

它不得包含 DOM element、Vue component、Vue Flow node 或 viewport state。

## 7. 子任务与实施顺序

### Step 1 — 冻结 topology specification 与 error catalog

**实施**

- 把第 3 节所有未决规则写入一个可测试的 Pattern specification table。
- 确定每种 kind 的 roles、cardinality、supported operations 和 route semantics。
- 区分 `moveAgent`、`exchangeAgents` 与 `reorderSlot`。
- 确定 route ID reconciliation 规则。
- 确定 duplicate transaction 的输入/输出及 ownership remap 范围。
- 更新 M2.3 plan 状态为 `Ready for implementation`。

**Gate**

- 不再需要从 Figma 像素或 fixture 猜 topology。
- 每条规则都可写成纯函数断言。
- 与 canonical `PatternConfig` shape 不冲突。

### Step 2 — 建立 definitions、ID factory 与 validation core

**实施**

- 为四种 built-in Pattern 建立 immutable definitions。
- 实现 strategy registry 的 exhaustive lookup。
- 实现 aggregate-level common validation：identity、route references、Agent uniqueness、kind/template consistency。
- 实现 per-kind validation：roles、cardinality、orders、derived routes 是否等于权威结果。
- 实现 deterministic `PatternIdFactory` test helper。

**测试**

- 四种合法 config；
- unknown/mismatched kind；
- duplicate Slot/Route/Agent；
- missing route endpoint；
- 非法 role/cardinality/order；
- routes structurally valid but semantically inconsistent。

### Step 3 — 实现四种 template instantiation 与 layout derivation

**实施**

- `instantiatePattern(templateKey, idFactory)` 一次生成完整合法 config。
- 四种 strategy 生成稳定 label、role、order 和 routes。
- `derivePatternPresentation(config)` 按 kind 生成 fixed/linear/radial/diamond layout。
- layout 只引用 Slot/Route UUID，不改变 config。
- 生成结果再次通过 runtime schema 和 domain validation。

**测试**

- deterministic factory 下精确输出；
- 所有 owned IDs 唯一；
- 同一 factory sequence 输出可复现；
- presentation 覆盖所有 Slots/Routes；
- config 不含 `x/y`；
- Figma 初始 topology 视觉意图得到结构性表达。

### Step 4 — 实现 assignment、move、exchange 与 unassign commands

**实施**

- `assignAgent(slotId, agentId)` 只允许空 Slot 和未占用 Agent。
- `moveAgent(sourceSlotId, targetSlotId)` 要求 source occupied、target empty。
- `exchangeAgents(firstSlotId, secondSlotId)` 交换 assignment，不交换 Slot identity、role、label 或 order。
- `unassignAgent(slotId)` 只清空 assignment，不删除 Agent aggregate。
- 所有 command 先验证候选新状态，再一次性返回；失败时输入保持不变。

**测试**

- success + 每个 precondition failure；
- Agent cardinality 始终 ≤ 1；
- non-linear exchange 后 roles/routes/layout 不变；
- input、nested arrays/objects 均不被 mutation；
- command result 通过 schema/domain validation。

### Step 5 — 实现 Slot add/remove、linear reorder 与 route reconciliation

**实施**

- 只开放 Step 1 specification 允许的 Slot operations。
- Linear add 默认 append，order 连续；remove/reorder 后重新编号。
- Hub add/remove 只作用于 spoke；hub identity/role 不变。
- Diamond 若 Step 1 未冻结动态位置，保持 fixed cardinality 并返回 `OPERATION_NOT_SUPPORTED`。
- 每次 topology 变化都从 Slots 派生 routes，并按 semantic endpoints reconcile route IDs。
- 删除 occupied Slot 的策略必须显式：默认拒绝，不能静默 orphan Agent。

**测试**

- Linear add/remove/reorder 的 slots、routes、layout；
- reorder 与 exchange 的差异；
- Hub 增删 spoke 后 topology；
- immutable role 不可删除；
- occupied Slot removal 被拒绝；
- retained routes 保留 ID、新 routes 获得新 ID、removed routes 消失。

### Step 6 — 实现 explicit Agent duplication/remap boundary

**实施**

- Pattern 层先执行 duplicate preflight：source configured、target empty、Agent 未重复。
- aggregate clone helper 深克隆 Agent、WorkflowGraph、CanvasLayout、Variables、Reusable Tools、Task-local Variables、Tool steps、Branch handles、Loop body owned IDs。
- external references（例如 Knowledge Space、System Variable）保持不变。
- 所有 owned internal references 按 ID map 重写。
- command 一次返回新 Agent document/summary 与新 Pattern assignment；任何失败不产生部分结果。
- 不在 M2.3 store 中直接保存；repository transaction/API 语义留给后续 integration，但纯结果必须可被原子提交。

**测试**

- 所有 owned IDs 与 source 不同且内部引用可解析；
- external IDs 保持；
- source aggregate 不变；
- duplicate 不能复用 target/source Agent ID；
- target occupied 和 invalid source 原子失败；
- cloned Agent document 通过 M2.1 runtime schema。

### Step 7 — Journey store 薄接入、invariant test matrix 与 handoff

**实施**

- 在 `journeyEditor` store 添加与 domain command 一一对应的 typed actions。
- store action 只负责读取当前 document、调用 command、提交成功结果/记录 domain error；不重复实现规则。
- M2.3 不触发 autosave，只为 M2.8 预留 dirty/mutation boundary。
- 加入 deterministic operation sequence tests；若不引入 `fast-check`，先用固定 seed/action table 覆盖组合序列。
- 加入 architecture scan，阻止 domain/pattern 导入 UI framework、DOM 或 repository。
- 写 M2.3 completion report 和 M2.4 handoff。

**测试矩阵**

- 四种 kind 的 instantiate → operations → validate；
- 多次 assign/move/exchange/unassign；
- Linear 多次 add/reorder/remove；
- Hub spoke 变更；
- 每一步验证 unique Slot/Route IDs、route endpoints、Agent cardinality、role invariants；
- save selector 仍只输出 persisted document；presentation layout 不进入 repository input。

## 8. 防 bug 规则

### 8.1 Candidate-first mutation

每个 command 必须：

```text
validate input
→ build candidate new state
→ derive/reconcile routes
→ validate candidate invariants
→ return candidate
```

不得先改输入对象、失败后回滚。

### 8.2 Identity 不依赖位置

- Slot identity 不因 reorder、Agent exchange 或 layout 变化而改变。
- route identity 按已冻结 reconciliation 规则处理。
- `order` 是 Linear topology data，不是 array index identity。
- presentation 坐标和 Figma node ID 不参与 command。

### 8.3 Operation semantics 不混淆

| Operation | Slot order/role | Agent assignment | Agent aggregate |
| --- | --- | --- | --- |
| move | 不变 | source → empty target | 不变 |
| exchange | 不变 | 两个 assignment 交换 | 不变 |
| reorder | Linear order 改变 | assignment 跟随 Slot identity | 不变 |
| duplicate | 不变 | target 获得新 Agent ID | 深克隆为新 aggregate |

### 8.4 Runtime schema 不替代 domain validation

Zod schema 负责 shape、UUID 和基本 references。M2.3 domain validation 负责 kind-specific cardinality、roles、route completeness、order、operation support 和 semantic topology。两者都必须执行和测试。

## 9. 实施批次建议

不建议一次完成全部 M2.3。推荐：

1. **Batch A — Step 1–3**：冻结 topology、validation、strategies、instantiation、layout；
2. **Batch B — Step 4–5**：assignment/move/exchange/unassign、Slot operations、route reconciliation；
3. **Batch C — Step 6–7**：Agent duplication/remap、store actions、组合 invariant tests、completion report。

每个 batch 独立 review。Batch A 的 topology specification 未 accepted 前不进入 Batch B/C。

## 11. 预期 handoff

M2.3 完成后，M2.4 可以稳定消费：

- built-in Pattern definitions；
- `PatternStrategy` registry；
- `instantiatePattern`；
