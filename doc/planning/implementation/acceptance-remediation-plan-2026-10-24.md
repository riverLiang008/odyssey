# Odyssey 验收整改实施计划

日期：2026-10-24  
状态：主要画布整改已实施；环境及复验范围见[实施记录](./acceptance-remediation-delivery-2026-10-24.md)。本文保留原计划内容。

依据：[整改 ToDo](./acceptance-remediation-todo-2026-10-24.md)、[原验收报告](../project/odyssey-acceptance-2026-10-23.md)、仓库前后端工程规范。

## 1. 范围与判断

本轮目标是修复现有编辑能力、恢复真实验收环境并补齐证据。FIX-01、FIX-02 是已确认缺陷；ENV-01 是环境阻塞；E2E-01 与 QA-01 是尚未完成的验收，不能预先认定存在实现缺陷。

不新增执行引擎、自动向量索引或运行时语义检索。不重复开发上轮已完成的 DSL Loop 两列布局、Preview 子节点展开规则和 Focus 保存控件。

当前工作区存在大量未提交修改，包含本轮可能触及的 Canvas、store、DSL、Preview、知识库及 API 文件。实施前必须逐文件确认现有差异，保留其他窗口成果；工作区差异本身不能证明某项问题已经解决。

## 2. 实施顺序与交付门槛

依赖顺序：基线确认 → FIX-01 → FIX-02 → E2E-01 → 综合回归与交付。ENV-01 在基线确认后尽早排查，E2E-01 必须等待 ENV-01 实际恢复；对象存储受阻不阻断两项画布修复及独立 QA。

### 阶段 A：确认基线与复现

1. 实施开始时重新完整阅读 AGENTS.md 及适用工程规范，记录 commit、已有差异与本轮修改边界。
2. 检查现有进程、端口、服务启动目录与配置，确认 Web/API/数据库对应当前源码；历史地址仅作线索，不随意重启其他服务。
3. 建立独立验收数据与截图目录，记录 Workspace、Journey、Agent、Knowledge Space 标识。
4. 按原步骤复现两个缺陷，保留同尺寸、同操作路径的修复前证据。若无法复现，先核对代码及数据差异，不直接宣布已修复。

交付：版本与服务基线、复现记录、专用数据标识。

### 阶段 B：FIX-01 模式切换视野

1. 追踪 WorkflowCanvas.vue、workflowCanvasAdapter.ts、workflowEditor.ts、AgentWorkflowView.vue 中模式派生坐标及 viewport 的转换，确认实际原因后定位修复。
2. 拟采用关注点保持策略：优先以当前可见的选中节点为锚点；无可用选中节点时，以当前可见节点或可见区域为锚点，将关注点映射到目标模式。具体规则以坐标模型核查结果定稿并记录。
3. 将模式切换协调留在 UI/adapter 边界；不重写业务图，不批量覆盖持久化节点布局，避免切换触发重复保存。明确临时切换视野与既有 viewport 保存/恢复规则的关系。
4. 补充坐标映射、双向切换及无漂移回归测试；浏览器覆盖根图/Loop、有无选中、平移与缩放、重复切换、1440×900、1024×900、Focus、保存刷新。

交付门槛：原失败步骤通过，原关注区域仍可浏览，业务配置与节点坐标无意外变更；附视野规则及前后对照证据。

### 阶段 C：FIX-02 Loop 实际尺寸约束

1. 核查节点 renderer 的展开规则、DOM 测量、adapter 坐标、创建入口及布局命令，确认尺寸何时可用及当前边界计算遗漏。
2. 拟采用最小布局调整策略：创建或内容增长时，先在有效区域内最小移动；卡片无法放入时按需扩大容器，尽量保留其他节点位置。容器缩小时约束最小尺寸，或在同一布局命令中完成合法的位置调整。最终策略须覆盖标题留白与出口可用性。
3. DOM 测量与 Vue Flow 数据留在 adapter；纯布局规则接收普通尺寸数据。持久化位置/尺寸通过 typed command 与应用事务一次提交，不由 renderer 直接改 store。
4. 对测量去重、稳定阈值及更新来源做明确处理，防止 ResizeObserver、布局更新和 autosave 循环；模式展示变化不能反复改写保存布局。
5. 测试新建 Branch/Task/Agent Action、所有创建入口、Case/条件增删、长名称、四边拖动、容器缩小/移动、不同模式和缩放。验证保存刷新、JSON 导入导出、DSL 重应用与只读 Preview，继续禁止嵌套 Loop。

交付门槛：实际浏览器测量证明卡片完整处于有效区域，内容及连线未被裁切；自动测试覆盖创建、动态尺寸与缩小容器，附持久化复验截图。

### 阶段 D：ENV-01 对象存储

1. 重新检查镜像、容器、网络与现有配置，复核历史下载失败原因。
2. 使用合法可用的 MinIO 或项目支持的 S3 兼容服务，验证健康、bucket、API endpoint、浏览器签名地址与 CORS。
3. 记录可复现启动步骤与配置项名称；凭据保留本地，不写入证据。只有真实 PUT 与后续读取成立才算恢复。
4. 如仍受阻，记录失败命令、脱敏错误、已尝试方案及剩余依赖，ENV-01/E2E-01 保持未完成；继续其他阶段。

### 阶段 E：E2E-01 真实知识库链路

1. 用独立 fixture，经页面创建知识库和目录，上传 Markdown，核对 prepare → PUT → complete、对象存在及刷新后的元数据和预览。
2. 编制并人工审阅匹配文件的 Manifest，执行 Validate → Preview → Apply，核对持久化索引/健康状态及当前页面的知识图谱展示。
3. 从真实资源列表，在根图和 Loop 的相关节点配置 Agent Action 知识库绑定及 Knowledge Retrieval，保存刷新并核对同一资源 ID。
4. 验证未索引、归档、失败及跨 Workspace 资源限制；覆盖上传中断、complete 失败及重试，失败不得残留虚假成功状态。
5. 若发现缺陷，先记录并定位边界，再按前后端规范修复及补测；不预先安排 API/数据库结构改动，不伪造索引状态。

交付：上传、Manifest 应用、绑定、刷新四阶段证据，以及服务和数据标识。结果只证明配置链路，不扩展为运行时检索效果结论。

### 阶段 F：QA-01 与保护性回归

逐项执行并记录结果，发现缺陷后形成单独复现条目并修复：

| 范围 | 核心检查 |
| --- | --- |
| 冲突 Overwrite | 双窗口、取消保留草稿、确认覆盖、覆盖中再次冲突/网络失败 |
| Branch | Case 排序与出口 identity、删除已连线 Case 的确认/取消、目标节点保留、长文本及焦点 |
| 连接与拖放 | 跨图/跨 Loop 非法连接、嵌套 Loop、资源与节点拖放串扰、失败无部分修改 |
| 保存时序 | 断网/失败/重试、保存中编辑、离开页面、旧响应晚返回、状态与草稿一致 |
| Preview | 长内容、动态高度、负坐标、Loop/特殊出口、缩放/resize、只读 |
| 视觉与可访问性 | 当前 Figma UI-25～29、已有对照文档、1440/1024、Focus、键盘与焦点恢复 |

无法获取 Figma 设计源时将相关项标记未验，不能用主观视觉检查代替。保护上轮已通过的 DSL 校验/离开保护、Reload、JSON 布局恢复、Loop 移动缩放、Preview 只读、Focus 保存状态、知识库创建刷新及未索引禁绑。

## 3. 检查与交付

- 每项先跑受影响模块测试，再执行前端 `pnpm check`；核对其是否覆盖 lint、typecheck、tests、production build，缺失部分单独补跑。
- 涉及后端时执行 Ruff check、format --check 和完整 pytest；使用专用真实 PostgreSQL 测试库。涉及迁移/初始化/CI 数据库配置时，另在专用空库迁移验证。
- 浏览器证据与自动测试分别记录实际范围、命令、退出结果及当前通过数量，不复制历史数字；远程 CI 只报告真实运行结果。
- 交付报告记录版本、已有修改与本轮文件、最终策略、编号状态、服务地址、数据 ID、浏览器尺寸、复现步骤、证据路径及剩余问题；脱敏凭据和签名 URL。
- 各编号只能按事实标记为“已实施待复验 / 仍阻塞 / 未执行”等状态。原 ToDo 的独立复验 checklist 保持未勾选，最终结论由原验收窗口给出。

本轮计划编写未修改产品代码，未启动或变更服务，未执行功能测试；以上技术策略为实施候选方案，须经源码核查与复现后确认。
