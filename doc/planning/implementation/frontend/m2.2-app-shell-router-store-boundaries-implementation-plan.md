# Odyssey M2.2 App Shell、Router 与 Store Boundaries Implementation Plan

> Status: Implemented; awaiting acceptance  
> Milestone: M2.2  
> Scope: 仅前端 application shell、路由、页面加载边界与 editor store 边界  
> Prerequisite: M2.1 accepted  
> Figma source: [Odyssey Design](https://www.figma.com/design/P3EF9io2DhyhwkNYBVqB5Z/Odyssey-Design?node-id=247-33)  
> Authoritative guideline: [`frontend-engineering-guidelines.md`](../../../frontend-engineering-guidelines.md)

## 1. 目标与交付结果

M2.2 要建立后续 Journey 与 Agent 编辑功能可以安全落地的应用骨架，并证明四类状态不会混在一起：

```text
route state          URL 中可恢复的页面身份与 tab
persisted document   repository 加载、保存的 Journey / Agent aggregate
editor session       selection、panel、mode、focus 等临时交互状态
persistence state    loading、saving、saved、error、conflict 等异步状态
```

完成后应具备以下可运行路径：

```text
Landing `/`
→ Open workspace
→ Journey List `/journeys`
→ Journey Editor `/journeys/:journeyId`
→ Agent Workflow Editor `/journeys/:journeyId/agents/:agentId`
```

本任务交付页面壳与数据加载闭环，不交付 Pattern 规则、Agent Slot 交互或 Vue Flow 画布。

## 2. 已确认的产品与设计决策

### 2.1 页面和路由

- 保留现有 `/` Landing 页面，不用 Figma application shell 覆盖或重写。
- Landing 的 **Open workspace** 是进入 V1 singleton Workspace 的导航操作，目标为 `/journeys`；不是 Workspace create。
- `/journeys` 使用 Figma `OdyJourney — Journey List` (`247:33`) 的可见 Journey List 内容。
- `/journeys/:journeyId` 是一个 Journey Editor 页面；Pattern、Execution、Behavior、Agent 是同一页面的 tab state。
- `/journeys/:journeyId/agents/:agentId` 是嵌套 Agent Workflow Editor 页面。
- Journey tab 使用规范化的 `tab` query；preview、panel、mode、focus 和 selection 不创建 route。
- 无效 UUID、记录不存在、repository 失败和未知 route 必须显示不同、可测试的 boundary。

### 2.2 Figma 解读

`247:33` 的正式 design context 显示以下 M2.2 视觉骨架：

- 1440 × 960 桌面参考画布；
- 204 px global navigation；
- 约 58–64 px product header；
- `#f8faff` 附近的内容画布、白色 panel/card、低对比蓝灰边框；
- Journey List 包含标题区、New OdyJourney、搜索/筛选 toolbar、分组和 Journey cards；
- global navigation 包含 Odyssey compact brand、Community、OdyJourney、Assets、Settings。

该 Figma frame 还包含被可见 Journey List 覆盖的 Knowledge Space 复制层。实现以 IA、frame 名称及可见 `Journey List / Content` 为准，不渲染这些残留层。Figma 输出的 React/Tailwind 仅用于层级和尺寸参考；代码必须实现为 Vue SFC，并复用项目 CSS、Naive UI 与 `@odyssey/design-tokens`，不引入 Tailwind。

### 2.3 M2.1 handoff

M2.2 直接复用以下稳定边界，不创建第二套 DTO：

- `JourneyEditorDocument`、`AgentWorkflowEditorDocument`；
- `EditorRepository`；
- `InMemoryEditorRepository`；
- deterministic Research System Journey/Agent fixtures；
- `RepositoryResult` 与结构化 `RepositoryError`。

## 3. 范围边界

### 3.1 必须完成

- application composition root 和单例 repository 注入；
- `/`、`/journeys`、Journey Editor、Agent Workflow Editor 和 not-found routes；
- shared `AppShell`、global navigation、product header 与 route outlet；
- Journey List 的 M2 fixture 展示与 Journey card navigation；
- `journeyEditor` 和 `workflowEditor` Pinia stores；
- route parameter/query runtime parsing；
- abort-aware repository load orchestration；
- loading、empty、error、not-found 页面状态；
- persisted document、session、persistence 的显式状态隔离；
- M2 所需基础语义 design tokens；
- route、store、页面 boundary 和核心导航测试。

### 3.2 明确不做

- Journey create、search 和 filter 的真实业务逻辑；控件可提供明确的 disabled/proof state；
- Pattern template 实例化、slot command 或 System Canvas 派生规则（M2.3–M2.5）；
- Vue Flow adapter、graph command 或 workflow canvas（M2.6–M2.8）；
- autosave debounce、stale response、conflict recovery UI（M2.8/M2.9）；
- real HTTP API adapter；
- Community、Assets、Settings 的完整页面；未实现入口使用 disabled/coming-soon 语义，不伪造可用 route；
- Figma 全屏逐像素复刻或移动端完整导航系统。

## 5. 子任务与实施顺序

### Step 1 — 冻结 M2.2 route contract 与 composition root

**实施**

- 定义有名称的 route records 和 typed navigation helpers。
- 为 `journeyId`、`agentId` 使用共享 UUID runtime schema，而不是字符串断言。
- 定义 Journey tab allowlist 和默认 tab；未知 query 值规范化到默认值。
- 在 application composition root 创建唯一 `EditorRepository` 实例，并通过 typed injection key 提供给 stores/use cases。
- 避免组件直接 `new InMemoryEditorRepository()`，确保 fixture revision 与实例隔离行为可预测。

**验收**

- route parser 对合法 UUID、非法 UUID、缺参和非法 tab 有确定结果。
- repository 依赖可以在测试中替换，不依赖全局可变 singleton。
- 本步骤不创建 editor domain command。

### Step 2 — 建立 shared App Shell 与基础 design tokens

**实施**

- 扩展 `@odyssey/design-tokens` 的语义 token：canvas、panel、surface、border、text、accent、success/warning/error、radius、shadow、spacing 和 shell dimensions。
- 实现 `AppShell`、`GlobalNavigation`、`ProductHeader` 和内容 outlet。
- 使用现有 Odyssey logo asset；保证 compact brand、active navigation 和 keyboard focus 可识别。
- application routes 使用 App Shell；Landing `/` 继续使用现有独立视觉。
- 窄桌面优先允许主内容横向最小宽度或 navigation 收缩；不允许 shell 覆盖关键 editor 区域。

**验收**

- `/` 不出现 application shell；`/journeys...` 共享同一 shell。
- 1440 px reference 下结构与 Figma 的 204 px navigation、product header 和内容区域一致。
- feature component 中不散落重复 raw hex；新增颜色优先来自语义 token。

### Step 3 — 完成 Landing → Journey List 入口与列表 proof

**实施**

- 将现有 disabled **Open workspace** 改为 router navigation 到 `/journeys`。
- 删除“Workspace creation arrives...”这类与已确认 singleton Workspace 决策冲突的文案。
- 实现 Journey List 的标题、toolbar shell、ownership sections 和 cards。
- 使用与 M2.1 Research System fixture 对齐的 deterministic summary projection；列表摘要是页面 read model，不复制 editor aggregate 为第二事实源。
- Journey card 导航到 `/journeys/:journeyId`。
- create/search/filter 在没有对应 use case 前保持清晰的 non-functional proof 状态，不做假交互。

**验收**

- 用户可从 Landing 进入 `/journeys`，浏览器 back 返回 Landing。
- 至少一个 fixture Journey 可打开。
- empty list 有独立状态；空数组不会被误判为 load failure。

### Step 4 — 实现 Journey Editor store 与页面加载 boundary

**状态结构**

```ts
interface JourneyEditorState {
  document: JourneyEditorDocument | null
  session: {
    activeTab: JourneyTab
    selectedSlotId: string | null
    previewAgentId: string | null
  }
  persistence: {
    loadStatus: 'idle' | 'loading' | 'ready' | 'not-found' | 'error'
    saveStatus: 'idle' | 'saving' | 'saved' | 'error' | 'conflict'
    error: RepositoryError | null
  }
}
```

**实施**

- store action 负责 repository load，组件不直接请求 repository。
- route 变化时取消上一请求或用 request identity 忽略 stale completion。
- load 新 Journey 前清理旧 document/session，避免短暂显示上一 Journey。
- active tab 从 route query 派生/同步；selected slot 和 preview 仅在 session。
- 页面只交付 Pattern、Execution、Behavior、Agent tab shell 和明确 placeholder，不实现领域交互。
- 提供 `toSaveInput(expectedRevision)` 或等价 selector，只从 `document` 生成 repository input。

**验收**

- direct navigation 和刷新可加载 fixture Journey。
- invalid UUID 不调用 repository；not-found 与 network/invalid-response error 分开显示。
- 快速切换 route 时旧响应不能覆盖新页面。
- session/persistence 字段不进入 save input。

### Step 5 — 实现 Workflow Editor store 与嵌套 route boundary

**实施**

- 建立与 Journey store 同构但独立的 `workflowEditor` state：document、session、persistence。
- session 至少预留 `selectedNodeId`、`panel`、`mode`、`focusMode`，并提供类型严格的 action；不创建 graph mutation。
- 先验证 route 中 Journey 存在，再加载 Agent；验证加载后的 Agent 归属当前 Journey，防止跨 Journey URL 拼接。
- Agent Workflow 页面展示 header、palette/canvas/panel 的结构 placeholder，以及返回 owning Journey 的导航。
- route 离开时 abort pending load 并清理临时 session。

**验收**

- nested route 可 direct navigation、刷新和 back 到 owning Journey。
- 非法/不存在/mismatched Journey-Agent 组合显示 not-found，不显示其他 Journey 的 Agent。
- mode、focus、selection、panel 不进入 Agent save input，也不写入 URL。

### Step 6 — 统一 loading、error、not-found 与重试行为

**实施**

- 建立可复用但不过度抽象的 route boundary presentation。
- loading 保持 shell 稳定，避免主导航和 header 闪烁重建。
- repository `NOT_FOUND`、`NETWORK`、`RESPONSE_INVALID`、`CONFLICT` 映射为明确用户状态；M2.2 的 load path 不把 conflict 当一般 not-found。
- retry 重新执行当前 route 的 load，并保持 request cancellation/stale guard。
- 添加未知 URL 的 Not Found 页面和返回 `/journeys` 的安全入口。

**验收**

- 每种失败状态有稳定文本/role，自动化测试无需依赖 CSS class 猜测状态。
- retry 不复用旧 error/document，也不会创建并行失控请求。
- boundary 不吞掉编程错误；仅处理已建模 repository/route failure。

### Step 7 — 自动化验证、视觉核对与 M2.3 handoff

**测试层级**

- unit：route contracts、tab normalization、save selectors、store state transitions、stale request guard；
- component：App Shell active navigation、Landing CTA、Journey cards、loading/error/not-found boundaries；
- router integration：direct navigation、back/forward、invalid params、nested ownership；
- repository integration：两个 stores 使用 M2.1 in-memory adapter 加载 deterministic fixtures；
- architecture audit：store/save input 不含 session 字段，schema/domain 不导入 Vue/Pinia/DOM。

**视觉验证**

- 以 Figma `247:33` 的 1440 px desktop screenshot 对照 shell、header、toolbar、cards 和 spacing hierarchy；
- 对 Journey Editor `59:2` 与 Workflow Editor `62:2` 只验证页面区域和层级，不在 M2.2 追求内部 canvas 视觉完成度；
- 检查 1024 px 左右桌面宽度下无关键控件覆盖；
- keyboard tab、focus-visible、landmark、heading hierarchy 和 loading announcement 可用。

**质量门**

```bash
pnpm check
```

完成报告需记录：实现的 routes、稳定 store interface、已覆盖的失败路径、Figma 偏差、明确 deferred items，以及 M2.3/M2.6 可以依赖的 exports。

## 6. 关键防 bug 约束

### 6.1 单一事实源

- persisted aggregate 只存在于 store `document`。
- component props/computed 是 projection，不复制可写 domain state。
- route params/query 由 router 决定；store 不另存一份可漂移的 `journeyId`/`agentId`。
- session state 不能为了刷新恢复而塞入 domain document。

### 6.2 异步安全

- 每次 route load 都绑定 AbortSignal 或 request identity。
- route 改变、store dispose 和组件卸载必须终止/失效旧请求。
- 只有当前 request 可以提交 `document`、`loadStatus` 和 `error`。
- load 开始前清除旧 aggregate；失败后不得保留看似可编辑的 stale document。

### 6.3 命令与写入边界

- M2.2 组件只调用 store action，不直接改 `document`。
- M2.2 不为方便 placeholder 而添加临时 Pattern/Workflow mutation。
- save selector 使用 M2.1 contract 构造 aggregate replacement input；禁止序列化整个 Pinia state。
- 后续 M2.3/M2.6 的 domain command 应能接入 store action，而无需重写页面组件。

### 6.4 类型与第三方边界

- route params、query 和 repository response 都是 runtime boundary，必须 parse 后使用。
- 不使用 `any`、双重断言或永久 `Record<string, unknown>` 逃逸。
- Vue Router/Pinia 类型不得泄漏到 `packages/schemas`。
- Figma/Tailwind/React 生成结构不得成为生产依赖或持久化模型。

## 8. 实施批次建议

M2.2 不建议一次性生成。推荐按以下三个可独立 review 的批次实施：

1. **Batch A — Step 1–3**：route contract、composition root、App Shell、Landing 与 Journey List；
2. **Batch B — Step 4–5**：Journey/Workflow stores、页面加载和 nested ownership；
3. **Batch C — Step 6–7**：failure boundaries、竞态测试、视觉/可访问性核对和 completion report。

每个 batch 都应先通过相关测试；Batch C 再执行完整 `pnpm check`。这样 M2.2 的问题可以定位到导航/壳层、状态加载或失败恢复中的单一边界，不需要在一次大改中同时排查。
