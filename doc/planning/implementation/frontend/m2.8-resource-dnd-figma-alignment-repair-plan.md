# M2.8 Resource DnD and Figma Alignment Repair Plan

> Status: Proposed for review
> Scope: Available Tool drag-and-drop into Agent Action Toolbox and Task sequence
> Visual authority: Figma `Agent Workflow Canvas — Resource Configuration`, node `98:2`
> Product authority: `doc/product/feature-specifications/resources/Update Agent Action Resource Configuration UI.md`
> Supersedes the browser/UI portions of: `m2.8-resource-drop-target-completion-plan.md`

## 1. Why this repair exists

The current implementation contains resource payload parsing, preflight rules and domain commands, but it does not yet deliver the complete browser interaction promised by M2.8.

The main failure is architectural and visual rather than a single missing `drop` listener:

- the Agent Action Toolbox is rendered as a narrow summary row instead of a usable resource zone;
- configured Tools are represented only by a count, so success and duplicate rejection are visually ambiguous;
- drag-over does not run target-aware preflight or expose valid/invalid state;
- current component tests prove DOM attributes and pure commands, but not the real HTML5 drag sequence;
- available acceptance data may contain only Tools that are already linked, hiding the successful path;
- nested Loop and root Canvas behavior has not been re-proven through the same browser matrix.

This repair treats resource drag-and-drop as one end-to-end interaction:

```text
Available Tool drag start
→ typed resource drag session
→ target-aware drag-over preflight
→ visible valid / invalid / duplicate feedback
→ nested target consumes the drop once
→ typed Canvas action
→ pure domain command
→ one canonical document mutation
→ autosave
→ reload persistence proof
```

## 2. Figma baseline to preserve

The implementation must follow the proportions and hierarchy of Figma node `98:2`, adapted responsively rather than copied as absolute page coordinates.

### 2.1 Overall composition

- Canvas is the full underlying editing stage.
- Workflow Node Palette floats over the left side of the Canvas at approximately `190px` wide.
- Available Tools panel floats over the right side at approximately `384px` wide.
- The central working corridor remains wide enough for the expanded nodes and their connections.
- Flow / Configure and Focus controls remain compact floating controls above the Canvas.
- The active top resource category uses text-only emphasis.

### 2.2 Agent Action expanded node

Target desktop size is approximately `360 × 300px`.

Its internal structure is:

```text
AGENT ACTION · Name
Model                         320 × 38
Goal                          320 × 44
Knowledge Spaces zone         320 × 58
Toolbox zone                  320 × 64
```

The Toolbox is a complete semantic region, not a count-only row:

- minimum height `64px` at the reference breakpoint;
- the whole bordered region is a drop target;
- title is always visible;
- bound Tools render as removable compact chips using Tool names;
- empty remaining space contains `+ Drop Tool`;
- the target may grow vertically or wrap chips when content increases;
- hit area must not shrink to the text baseline or individual chip.

### 2.3 Task expanded node

Target desktop size is approximately `460 × 190px` for the Figma example.

- the full sequence body is a Tool drop target;
- each Tool step is a `430 × 30px`-style row at the reference breakpoint;
- rows show sequence number, Tool label and input/output summary;
- dropping on the empty body appends to the end;
- dropping between rows may expose an insertion indicator if insertion-index support is included in this repair;
- the target grows with its step count instead of clipping the sequence.

### 2.4 Available Tools panel

- reference width: `384px`, with `16px` internal padding;
- Tool cards are approximately `352 × 58px`;
- cards expose a clear drag affordance and use the whole card as the drag source;
- search, filters and resource list stay stable while dragging;
- the footer explicitly says: `Drag a Tool to an Agent Action Toolbox or Task sequence.`

## 3. Frozen product semantics

### 3.1 Agent Action Toolbox

- Drop binds an existing Agent reusable Tool by ID.
- One Tool ID is unique within a single Agent Action Toolbox.
- Duplicate drops are rejected without mutation.
- A bound Tool remains in the Available Tools inventory; the library is not consumed.
- Bound Tool chips are derived from canonical `node.config.reusableToolIds` joined with `document.reusableTools`.
- Removing a chip unbinds through the existing typed command and autosave path.

### 3.2 Task sequence

- Every successful Tool drop creates a new Task-owned `ToolStep`.
- Repeated use of the same reusable Tool is allowed because each step has its own ID.
- Default behavior remains append-to-end unless an explicit insertion index is supplied.
- Generated configuration, output mapping and local output variable remain owned by the existing pure Task command.
- The visible Task rows derive from canonical `Task.config.steps`.

### 3.3 Mode and scope

- Resource drag targets are active only in Configure mode.
- Flow mode may show configured resources read-only but does not accept resource drops.
- Root and Loop-child Agent Action/Task nodes follow identical rules within isolated Canvas contexts.
- Dropping a resource on the Canvas pane never creates a Workflow node.
- Dropping a Workflow node template on a resource zone never binds a resource.

## 4. Interaction state machine

Add one session-only discriminated resource drag state rather than independent component booleans:

```ts
type WorkflowResourceDragState =
  | { type: 'idle' }
  | {
      type: 'dragging-resource'
      payload: WorkflowResourceDragPayload
      target: WorkflowResourceDropTarget | null
      evaluation: WorkflowResourceDropEvaluation | null
    }
```

Required transitions:

1. `resource-drag-started`
2. `resource-target-entered`
3. `resource-target-moved`
4. `resource-target-left`
5. `resource-drop-committed`
6. `resource-drop-rejected`
7. `resource-drag-ended`
8. `Escape` → idle

The state is never persisted and never copied into WorkflowGraph or CanvasLayout.

## 5. Event ownership and arbitration

### 5.1 Drag source

`WorkflowResourceBrowser` owns browser `dragstart`/`dragend` only:

- serialize the typed payload to the Odyssey MIME and `text/plain` compatibility channel;
- emit a typed `resourceDragStart`/`resourceDragEnd` intent;
- set an explicit drag image only if the browser default is visually inadequate;
- do not mutate the Agent document.

### 5.2 Semantic target component

Introduce or extract reusable presentational targets, for example:

- `AgentActionToolboxZone.vue`
- `TaskToolSequenceZone.vue`

Each zone owns its own browser boundary:

- `dragenter`, `dragover`, `dragleave`, `drop`;
- target identity and accessible label;
- `preventDefault` only when handling a known resource drag;
- `stopPropagation` for a recognized nested resource drop;
- emit a typed target intent; never modify node configuration directly.

The Canvas remains the central coordinator and pane fallback, but it must not infer a valid nested target solely from a late pane-level `event.target` lookup.

### 5.3 Preflight

Every target entry/move calls the existing pure `evaluateWorkflowResourceDrop` using:

- parsed payload;
- typed target;
- canonical target node;
- current Agent reusable Tool inventory.

Only `status: valid` permits a commit. Rejection leaves graph, layout, mutation sequence and revision unchanged.

## 6. Visual feedback

### 6.1 Valid target

- preserve the Figma zone border color;
- add a restrained blue/green focus ring or tinted background;
- show `Drop to add` or an insertion indicator;
- use `dropEffect = copy`.

### 6.2 Invalid target

- do not render a large red rectangle or page-wide alert during hover;
- show a prohibited cursor and a compact local indication;
- use `dropEffect = none`;
- distinguish wrong resource type, unavailable Tool and duplicate Tool through accessible status text.

### 6.3 After drop

- successful Agent Action binding immediately renders the Tool chip;
- successful Task insertion immediately renders exactly one new numbered step;
- duplicate binding keeps the Toolbox unchanged and shows a small local `Already added` message;
- drag visual state always clears after drop, dragend, route change or Escape.

## 7. Implementation sequence

### Phase A — UI structure and proportions

1. Extract the Agent Action Toolbox and Task sequence into semantic drop-zone components.
2. Align expanded Agent Action to the Figma `360 × 300` reference and give Toolbox a `320 × 64` minimum usable region.
3. Render real Tool chips with names and remove actions instead of only `N linked`.
4. Align expanded Task to the `460px` reference width and render responsive `30px` step rows.
5. Keep the `384px` floating resource browser and protect the central Canvas corridor at desktop and 1024px breakpoints.

### Phase B — browser interaction

6. Add the session-only resource drag state and typed transitions.
7. Wire drag source start/end from the Available Tools cards.
8. Wire target enter/over/leave/drop in the semantic target components.
9. Run pure preflight during drag-over and expose the evaluation as view state.
10. Consume valid nested drops once and retain Canvas pane rejection as a fallback.
11. Apply the same target components and coordinator contract inside Loop child Canvas.

### Phase C — command, persistence and recovery verification

12. Reuse `bindWorkflowAgentActionReusableTool` for Toolbox binding.
13. Reuse `appendWorkflowTaskToolStep` for Task insertion.
14. Verify one successful drop advances the local mutation sequence exactly once.
15. Verify autosave, revision advancement and refresh restoration.
16. Verify failed and duplicate drops do not dirty the document.

### Phase D — accessibility and alternative paths

17. Keep Tool cards keyboard focusable.
18. Add a click/keyboard `Add to…` path using the same target/action contract; drag must not be the only usable path.
19. Announce successful or rejected resource operations through a compact live region.
20. Ensure Escape cancels the drag UI state without changing canonical data.

## 8. Test strategy

### 8.1 Pure tests

- resource payload parse/validation;
- Tool × target cross-matrix;
- duplicate and unavailable rejection;
- Agent Action bind/unbind immutability;
- Task step generation, repeated Tool use and ordering;
- rejection leaves input unchanged.

### 8.2 Component tests

- Tool card emits start/end typed intents;
- Toolbox and Task zones expose their full region as the target;
- valid/invalid/duplicate visual states;
- nested valid drop is emitted once and stops pane consumption;
- bound Tool names/chips derive from props;
- chip removal emits an unbind intent;
- Flow mode is read-only and Configure mode accepts resources.

### 8.3 Integration tests

- Available Tool → unbound root Agent Action Toolbox;
- Available Tool → root Task;
- Available Tool → Loop-child Agent Action Toolbox;
- Available Tool → Loop-child Task;
- resource → Canvas pane does not create a node;
- Workflow node template → Toolbox does not bind a Tool;
- duplicate Agent Action drop does not dirty the document;
- repeated Task drop appends distinct step IDs;
- changing mode or context clears drag state.

### 8.4 Real-browser acceptance

Use a real API aggregate containing:

- at least one reusable Tool not bound to the target Agent Action;
- one root Agent Action;
- one root Task;
- one Loop-child Agent Action;
- one Loop-child Task.

For every successful path verify:

```text
visible drag feedback
→ visible content change
→ one mutation
→ autosave completes
→ revision advances
→ refresh preserves the result
```

Real HTML5/pointer drag must be exercised in Chromium. jsdom attribute tests are not sufficient for PASS.

## 9. Acceptance criteria

- The expanded Agent Action and Task match the Figma hierarchy and usable proportions at 1440px.
- Toolbox has a full-width, minimum `64px` drop area and shows named Tool chips.
- Task exposes its full sequence body as the target and shows ordered Tool rows.
- A previously unbound Tool can be dragged successfully into root and Loop-child Toolboxes.
- A Tool can be dragged successfully into root and Loop-child Tasks.
- Valid, invalid and duplicate hover/drop states are visibly distinguishable without a large red rectangle.
- A valid nested target consumes exactly one drop.
- Resource drops never create Workflow nodes.
- Failed drops never mutate or schedule autosave.
- Successful changes survive autosave and refresh through the real Web API.
- Equivalent click/keyboard addition uses the same typed command boundary.
- Lint, typecheck, tests and production build all pass.

## 10. Non-goals

- Tool Definition or Tool Template CRUD;
- arbitrary Tool parameter editors beyond existing schemas;
- Task step drag-reordering unless insertion-index support is explicitly accepted;
- cross-Agent Tool transfer;
- persistence of drag/hover state;
- replacing Vue Flow or changing Workflow graph invariants.
