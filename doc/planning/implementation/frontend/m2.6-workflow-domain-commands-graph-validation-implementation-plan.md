# Odyssey M2.6 Workflow Domain Commands 与 Graph Validation Implementation Plan

> Status: Proposed — ready for review before implementation  
> Milestone: M2.6  
> Scope: framework-neutral Workflow graph factories、typed domain commands、structural validation、execution-readiness diagnostics 与 Workflow Editor store integration  
> Prerequisite: M2.1 contracts accepted；M2.5 accepted  
> Authoritative guideline: [`frontend-engineering-guidelines.md`](../../../frontend-engineering-guidelines.md)  
> Authoritative contract: [`canonical-json-contracts-draft.md`](../../../architecture/data/contracts/canonical-json-contracts-draft.md)  
> Execution semantics: [`Canvas Execution Model.md`](../../../architecture/execution/Canvas%20Execution%20Model.md)  
> Parent plan: [`m2-interaction-proof-frontend-implementation.md`](./m2-interaction-proof-frontend-implementation.md)

## 1. Outcome

M2.6 在 Vue Flow editable canvas 接入前建立唯一的 Workflow mutation authority：

```text
UI / future Vue Flow event
→ typed Workflow intent
→ pure domain command
→ validate candidate graph
→ success(new graph) | failure(stable error)
→ Workflow Editor store atomically replaces document graph
```

完成后，M2.7 只负责把 Canvas event 转换为 intent，不得自行维护节点、连线、Branch handle、Loop 或 DAG 规则。

M2.6 的成功标准不是“能修改数组”，而是任意成功 command 序列都不会破坏 Workflow 的结构安全；任意失败 command 都不会改变输入 graph、layout 或 store document。

## 2. Frozen boundaries

### 2.1 Sources of truth

优先级如下：

1. accepted and frozen V1 JSON contract；
2. `@odyssey/schemas` runtime schema 与 inferred types；
3. accepted execution semantics；
4. 本计划对 command、validation severity 和实施顺序的冻结；
5. Canvas/Figma 只决定 presentation，不决定 domain structure。

不得创建替代性的 Workflow/Node/Edge interface。Domain 直接消费 `@odyssey/schemas` 的 `WorkflowGraph`、`WorkflowNode`、`WorkflowEdge` 和各节点 config 类型。

### 2.2 Graph、layout 与 session

M2.6 严格保持：

```text
WorkflowGraph  = semantic nodes + edges + node configuration
CanvasLayout   = placements + viewport
Editor session = selection + panel + mode + future interaction state
```

- graph command 只返回新 `WorkflowGraph`；
- 不读取或修改 `CanvasLayout`；
- 不处理 node position、viewport、selection、panel、focus 或 DOM event；
- 删除节点后的 layout reconciliation 留给 M2.7 的 application transaction，不偷偷放入 graph domain；
- domain 不导入 Vue、Pinia、DOM、Vue Flow、router、repository 或 HTTP。

### 2.3 Node kinds and V1 configuration

Top-level graph 允许：

- `start`、`end`；
- `agent_action`；
- `task`；
- `branch`；
- `loop`。

Loop body 允许：

- `loop_start`、`loop_end`；
- `agent_action`、`task`、`branch`；
- 不允许普通 `start/end`；
- 不允许 nested `loop`。

V1 Loop termination 以冻结 schema 为准，只实现 `variable_comparison + maxTurns`。概念文档中的 LLM evaluator 不进入 M2.6。

### 2.4 System-owned boundary nodes

“implicit Start/End”解释为 system-owned，而非不持久化：

- top-level graph 显式持久化恰好一个 Start 和一个 End；
- Loop body 显式持久化恰好一个 Loop Start 和一个 Loop End；
- factory 自动创建；
- command 不允许用户新增第二个或删除/改型这些 boundary nodes；
- boundary node 的 display name 可以保留 contract 字段，但 M2.6 不提供修改 boundary identity semantics 的入口。

## 3. Validation model

### 3.1 Why validation is split

编辑中的 graph 可能暂时尚未连完，但绝不能出现引用损坏、非法 handle 或 cycle。因此 M2.6 将 validation 分为两层：

```ts
validateWorkflowStructure(graph, context)
validateWorkflowReadiness(graph, context)
```

#### Structural validation — command hard gate

任何 command 成功后必须满足，违反时拒绝 mutation：

- runtime contract 可解析；
- node ID、edge ID 唯一；
- edge endpoints 存在；
- 无 self-edge；
- 无 duplicate semantic edge；
- graph 为 DAG；
- handle 与 source node 兼容；
- Branch handle 属于 source Branch；
- 非 Branch edge 不含 `sourceHandleId`；
- top-level 与 Loop body 的 allowed node kinds 正确；
- boundary node cardinality、类型和 delete protection 正确；
- Start/Loop Start 无 incoming；
- End/Loop End 无 outgoing；
- Loop body 不包含 nested Loop；
- Loop body graph/layout 满足 frozen schema reference rules。

#### Execution readiness — diagnostic gate

用于决定 graph 是否可执行/发布，不阻止正常的逐步编辑：

- 所有非 Start 节点可从 Start 到达；
- 所有非 End 节点存在通向 End 的路径；
- Start 至少一条 outgoing，End 至少一条 incoming；
- 普通 action/task/loop 的 incoming/outgoing 满足可执行要求；
- Branch 每个 Case 和 Default handle 恰好一条 outgoing edge；
- Branch 不存在无 handle 的 outgoing edge；
- Loop body 从 Loop Start 可到达 Loop End；
- Loop body 节点满足相同 reachability/co-reachability；
- config 中跨对象引用的完整性在具备 Agent variables/tools/knowledge context 时检查。

`validateWorkflowGraph` 返回两组 diagnostics：

```ts
interface WorkflowValidationReport {
  readonly structuralErrors: readonly WorkflowValidationIssue[]
  readonly readinessErrors: readonly WorkflowValidationIssue[]
  readonly isStructurallyValid: boolean
  readonly isExecutionReady: boolean
}
```

Validator 只返回稳定 code、entity IDs 和必要 metadata，不返回最终 UI 文案。

### 3.2 Contexts

同一套算法支持两种显式 context：

```ts
type WorkflowGraphContext =
  | { kind: 'agent-workflow' }
  | { kind: 'loop-body'; loopNodeId: UUID }
```

禁止通过扫描到 `loop_start` 后猜测 context。Nested Loop 的 child graph 必须由 parent Loop command 显式调用 loop-body validator。

### 3.3 Duplicate edge identity

semantic duplicate 冻结为相同：

```text
sourceNodeId + normalized sourceHandleId + targetNodeId
```

其中缺失与 contract-normalized `undefined` 等价。不同 Branch handle 指向同一 target 是两条不同 route，不视为 duplicate。

### 3.4 Cycle and reachability algorithms

- edge candidate 连接前先做 O(1) preconditions，再在 candidate adjacency 上做 DFS/Kahn cycle detection；
- full validation 使用 node/edge index 和 adjacency/reverse-adjacency，一次构建、多个规则复用；
- 不在 pointer move 或 layout update 时运行 graph validation；
- 测试记录大图基准，避免明显的重复全数组扫描；
- M2.6 不做过早 cache，先保持纯函数和可证明正确性。

## 4. Domain error and diagnostic contract

### 4.1 Command errors

建议冻结为 discriminated union：

```ts
type WorkflowDomainError =
  | { code: 'INVALID_SOURCE_GRAPH'; issues: readonly WorkflowValidationIssue[] }
  | { code: 'NODE_NOT_FOUND'; nodeId: UUID }
  | { code: 'EDGE_NOT_FOUND'; edgeId: UUID }
  | { code: 'NODE_ID_CONFLICT'; nodeId: UUID }
  | { code: 'EDGE_ID_CONFLICT'; edgeId: UUID }
  | { code: 'BOUNDARY_NODE_IMMUTABLE'; nodeId: UUID }
  | { code: 'NODE_KIND_NOT_ALLOWED'; nodeType: string; context: WorkflowGraphContext }
  | { code: 'MISSING_ENDPOINT'; endpoint: 'source' | 'target'; nodeId: UUID }
  | { code: 'SELF_EDGE'; nodeId: UUID }
  | { code: 'DUPLICATE_EDGE'; sourceNodeId: UUID; sourceHandleId?: UUID; targetNodeId: UUID }
  | { code: 'INVALID_EDGE_DIRECTION'; sourceNodeId: UUID; targetNodeId: UUID }
  | { code: 'HANDLE_REQUIRED'; branchNodeId: UUID }
  | { code: 'HANDLE_NOT_ALLOWED'; sourceNodeId: UUID }
  | { code: 'HANDLE_NOT_FOUND'; branchNodeId: UUID; sourceHandleId: UUID }
  | { code: 'HANDLE_ALREADY_CONNECTED'; branchNodeId: UUID; sourceHandleId: UUID }
  | { code: 'CYCLE_DETECTED'; sourceNodeId: UUID; targetNodeId: UUID }
  | { code: 'INVALID_NODE_CONFIG'; nodeId: UUID }
  | { code: 'INVALID_LOOP_BODY'; loopNodeId: UUID; issues: readonly WorkflowValidationIssue[] }
```

如果实现时发现两个 code 永远无法被调用，应在 completion report 说明并删除，不能保留无测试的装饰性 union member。

### 4.2 Validation issue codes

至少覆盖：

```text
DUPLICATE_NODE_ID
DUPLICATE_EDGE_ID
MISSING_EDGE_SOURCE
MISSING_EDGE_TARGET
SELF_EDGE
DUPLICATE_EDGE
CYCLE_DETECTED
START_CARDINALITY
END_CARDINALITY
LOOP_START_CARDINALITY
LOOP_END_CARDINALITY
START_HAS_INCOMING
END_HAS_OUTGOING
INVALID_NODE_KIND
INVALID_SOURCE_HANDLE
BRANCH_ROUTE_INCOMPLETE
BRANCH_ROUTE_DUPLICATE
UNREACHABLE_FROM_START
CANNOT_REACH_END
INVALID_LOOP_BODY
INVALID_CONTRACT
```

Issue 必须含 `path` 或相关 entity ID，使 M2.7 可以高亮对应 node/edge，而不解析英文错误字符串。

## 5. Command contract

所有 command：

- 接收 readonly-style domain input；
- 开始时验证 source graph structural safety；
- 使用 `structuredClone` 或局部 immutable reconstruction 创建 candidate；
- 只验证 candidate，不先修改 source 再回滚；
- 成功返回独立的新 graph；
- 失败不生成部分结果；
- ID 由注入的 factory 产生，不在测试里依赖随机 UUID；
- 不保存、不 toast、不导航、不修改 session/layout。

### 5.1 Factories

```ts
createMinimalAgentWorkflow(idFactory)
createMinimalLoopBody(idFactory)
createDefaultNode(nodeType, idFactory)
```

- Agent factory：Start、End、默认 edge；
- Loop body factory：Loop Start、Loop End、默认 edge；
- 默认 Agent Action/Task/Branch/Loop config 必须通过现有 runtime schema；
- Branch 默认包含 required Default Case；Cases 可以为空；
- Loop 默认 body 已是最小合法结构；
- 默认 model、goal、exit variable 等若无法由 domain 合理决定，则 factory intent 必须显式携带，不得硬编码虚假的业务资源 ID。

### 5.2 `addNode`

输入包含完整合法 node 或严格 typed creation intent。冻结行为：

- 拒绝 ID collision；
- 拒绝 context 不允许的 node kind；
- 不创建 placement；
- 新增普通节点可以暂时 disconnected，因此成功后可能 not-ready，但必须 structurally valid；
- 不允许使用该 command 新增 Start/End/Loop Start/Loop End。

### 5.3 `removeNode`

- node 必须存在；
- boundary node 拒绝删除；
- 原子删除 node 及所有 incident edges；
- 不自动重连 predecessor/successor，不猜测用户意图；
- 若删除 Branch/Loop，整个 config/body 随 owner node 删除；
- command 结果可以产生 readiness diagnostics，但不得破坏 structural invariants。

### 5.4 `updateNodeConfig`

- 使用按 node type 判别的 typed intent，不接受 `Record<string, unknown>` patch；
- node identity 和 type 不可通过 config command 修改；
- candidate node 必须通过对应 runtime schema；
- 更新 Branch config 时同步校验 handle references；
- 删除 Branch Case 必须使用专用原子 command 或提供 edge reconciliation policy，不能留下引用已删除 handle 的 edge；
- 更新 Loop config/body 时递归验证 child graph；
- config command 不改变 layout。

为避免一个过宽 command 隐藏复合语义，建议同时提供：

```text
addBranchCase
removeBranchCase       # 原子删除 Case 与对应 outgoing edge
reorderBranchCase
updateBranchCase
updateLoopSettings
applyLoopBodyCommand   # child command 结果原子写回 parent Loop
```

M2.6 至少完成基础实现和测试；最终配置 panel 可由 M2.7/M4 消费。

### 5.5 `connectNodes`

顺序冻结为：

1. source/target existence；
2. self-edge；
3. Start/End/Loop boundary direction；
4. handle compatibility and ownership；
5. Branch handle cardinality；
6. duplicate semantic edge；
7. edge ID collision；
8. candidate cycle detection；
9. full candidate structural validation；
10. return new graph。

Branch source 必须提供合法 `sourceHandleId`；非 Branch source 必须省略。一个 Branch Case/Default handle 最多一条 outgoing edge。

### 5.6 `removeEdge`

- edge 必须存在；
- 返回删除该 edge 的 structurally valid graph；
- 可以造成 disconnected 或 Branch route incomplete，作为 readiness diagnostic 暴露；
- 不自动创建替代 edge；
- 最小 factory edge 不是 immutable，用户未来可以通过正常编辑替换路径；但删除后 graph 不能被当作 execution-ready。

## 6. Store integration

M2.6 只完成 command 接入，不提前实现 M2.7 Canvas UI。

`workflowEditor` store 新增一个统一入口，例如：

```ts
applyGraphCommand(command): WorkflowApplicationResult
```

或若保持显式 action：

```text
addWorkflowNode
removeWorkflowNode
updateWorkflowNodeConfig
connectWorkflowNodes
removeWorkflowEdge
```

Store responsibilities：

- 校验当前 document identity；
- 调用 pure domain command；
- 成功时一次替换 `document.workflow`；
- mutation sequence/dirty persistence 若尚未进入当前 store，则只建立明确 extension point，不伪造 autosave；
- 失败时保存可展示的 last domain error 或直接返回 caller，不能修改 document；
- 删除 selected node 后稳定关闭/清理相关 session panel；
- 不让 domain error 混入 repository error；
- `toSaveInput()` 只包含成功后的 graph，不包含 diagnostics/session。

M2.6 不新增后端 endpoint。持久化继续复用现有 `saveAgentWorkflow` aggregate replacement contract；实际 autosave race orchestration 仍按父计划后续里程碑实施。

## 8. Implementation sequence

### Step 0 — Contract audit and test fixture inventory

交付：

- frozen invariant matrix：top-level、Loop body、per-node edge rules；
- contract examples 与现有 fixtures 的合法性检查；
- source schema 只负责 JSON shape、M2.6 负责 mutation invariant 的边界记录；
- 确认没有 Vue Flow/private node type 被引入 domain。

Gate：所有后续测试都引用同一 invariant matrix，不在不同 test 文件发明不同规则。

### Step 1 — Error、issue、context and ID factory contracts

交付：

- `WorkflowGraphContext`；
- `WorkflowDomainError`；
- `WorkflowValidationIssue/Report`；
- injectable deterministic ID factory；
- exhaustive error code tests/type assertions。

Gate：M2.7 能通过 code + IDs 映射 UI feedback，不解析 message。

### Step 2 — Graph index and structural validator

交付：

- node/edge maps；
- adjacency/reverse adjacency；
- duplicate、endpoint、handle、boundary、allowed-kind checks；
- DAG detection；
- recursive Loop body validation；
- validator 不修改输入。

Gate：canonical fixtures 通过，针对每个 structural issue 的单一失败 fixture 精确返回预期 code/path。

### Step 3 — Readiness diagnostics

交付：

- Start reachability 与 End co-reachability；
- Branch route completeness；
- Loop body readiness；
- structurally valid draft 与 execution-ready graph 的明确区分。

Gate：disconnected node/刚创建 Branch 可以作为草稿存在，但 `isExecutionReady === false`；cycle、dangling edge、invalid handle 永远不能作为成功 command 结果存在。

### Step 4 — Minimal factories and default nodes

交付：

- minimal Agent graph；
- minimal Loop body；
- default creation intents/config builders；
- deterministic IDs；
- schema parse + structural/readiness tests。

Gate：factory output 通过 runtime schema、structure validation 和 readiness validation；没有虚假资源引用。

### Step 5 — Basic node and edge commands

按风险从低到高实现：

1. `addNode`；
2. `removeNode`；
3. `removeEdge`；
4. `connectNodes`；
5. `updateNodeConfig`。

每个 command 同时完成：happy path、所有 precondition errors、input immutability、rejected candidate atomicity 和 graph/layout separation assertions。

Gate：失败 command 的输入 JSON、object identity-observable content 和 store document 均不变。

### Step 6 — Branch and Loop compound commands

交付：

- Branch Case add/remove/reorder/update；
- Case removal 与 route removal 原子化；
- Loop settings update；
- child Loop body command application；
- child failure 不修改 parent Loop 或 top-level graph；
- nested Loop rejection。

Gate：Branch handle 和 outgoing edge 永不产生 dangling reference；Loop child command 不污染 parent layout/session。

### Step 7 — Workflow Editor store integration

交付：

- typed store actions/application result；
- atomic document graph replacement；
- selected node/panel reconciliation；
- domain/repository/session error separation；
- `toSaveInput()` regression tests。

Gate：组件未来无需直接接触 graph arrays；store 失败路径不改变 graph、layout、revision 或 save payload。

### Step 8 — Invariant sequence, mutation and performance tests

交付：

- deterministic generated legal command sequences；
- random sequence/property tests；
- source graph and result aliasing tests；
- moderate/large DAG validation benchmark guard；
- Loop child graph sequence tests。

如果不引入 `fast-check`，使用固定 seed 的本地 generator，失败时打印 seed 和 command sequence，确保完全可复现。未经统一评审不为单一里程碑随意增加测试依赖。

Gate：任意成功序列持续满足 structural invariant；任意失败步骤保持上一状态字节等价；测试无 flaky randomness。

### Step 9 — Full gates and handoff

运行：

```bash
pnpm lint
pnpm typecheck
pnpm test
pnpm build
```

交付：

- M2.6 completion report；
- independent acceptance checklist/prompt；
- stable exports and error-code inventory；
- M2.7 handoff：intent signatures、command results、readiness diagnostics、graph/layout transaction boundary；
- deferred items 与任何 contract review 明确记录。

## 9. Test matrix

### 9.1 Factories

| Scenario | Expected |
| --- | --- |
| minimal Agent Workflow | exactly Start + End + one edge，ready |
| minimal Loop body | exactly Loop Start + Loop End + one edge，ready |
| deterministic factory | same injected sequence produces same graph |
| ID collision | stable ID conflict，no partial graph |
| default node | config parses with matching discriminant |

### 9.2 Node commands

| Scenario | Expected |
| --- | --- |
| add disconnected action | succeeds structurally，readiness reports disconnected |
| add second Start/End | rejected |
| add Loop to Loop body | rejected |
| remove ordinary node | node + incident edges removed atomically |
| remove boundary node | `BOUNDARY_NODE_IMMUTABLE` |
| update config with wrong shape | `INVALID_NODE_CONFIG` |
| update config | graph changes；layout/revision/session unchanged by domain |

### 9.3 Edge commands

| Scenario | Expected |
| --- | --- |
| missing source/target | stable missing endpoint error |
| self edge | rejected |
| semantic duplicate | rejected regardless of edge ID |
| duplicate edge ID | rejected |
| edge into Start/Loop Start | rejected |
| edge out of End/Loop End | rejected |
| back edge creates cycle | rejected，source graph unchanged |
| non-Branch with handle | rejected |
| Branch without handle | rejected |
| unknown/foreign Branch handle | rejected |
| second edge from same Branch handle | rejected |
| remove required Branch route | succeeds as draft；readiness incomplete |

### 9.4 Readiness

| Scenario | Expected |
| --- | --- |
| disconnected node | structurally valid，not ready |
| node reachable from Start but cannot reach End | not ready |
| complete Branch Cases + Default | ready if all paths reach End |
| missing Branch route | not ready with handle identity |
| valid Loop body | parent can be ready |
| incomplete Loop body | parent structure remains safe，not ready |

### 9.5 Atomicity and boundaries

| Scenario | Expected |
| --- | --- |
| rejected command | input graph deep-equal and store document unchanged |
| successful command | returned graph does not alias mutable input collections |
| graph command | layout byte/deep-equal unchanged |
| child Loop failure | parent graph unchanged |
| store save projection | contains graph/layout domain only，no diagnostics/session/error |
| domain import audit | no Vue/Pinia/DOM/Vue Flow/router/repository/HTTP imports |

## 10. Acceptance criteria

M2.6 只有同时满足以下条件才可验收通过：

1. minimal Agent Workflow 和 minimal Loop body factory 可复用且完全 deterministic-testable；
2. typed node/edge/config commands 全部通过 pure domain functions；
3. Start/End 与 Loop boundary cardinality、direction 和 delete protection 生效；
4. missing endpoint、self、duplicate、invalid handle、cycle 使用稳定 error code 拒绝；
5. arbitrary cycles 被拒绝，Loop 是唯一的 repetition representation；
6. Branch Case/Default identity 与 outgoing handle rule 被验证；
7. Loop body 独立验证、禁止 nested Loop；
8. structural validity 与 execution readiness 明确分层；
9. rejected command 不改变 graph、layout、store document 或 save projection；
10. graph domain 不依赖 Vue、Pinia、DOM、Vue Flow、router、repository 或 HTTP；
11. store 只通过 command result 原子替换 Workflow graph；
12. property/sequence tests 证明成功序列持续保持 DAG 与 identity/reference invariants；
13. canonical fixtures、M2.4/M2.5 regression tests 保持通过；
14. lint、typecheck、全部 tests、production build 全绿。

## 11. Explicitly deferred

- Vue Flow nodes/edges 和 editable Canvas adapter：M2.7；
- node palette、drag placement、connect gesture、keyboard delete UI：M2.7；
- node position、viewport、selection、Focus Mode：M2.7/M2.8；
- Loop nested Canvas 最终 UI 与独立 viewport/session：M2.8；
- Tool/Knowledge Space resource DnD：后续对应里程碑；
- autosave debounce、stale response、revision conflict UI：M2.8/M2.9；
- LLM evaluator Loop exit strategy、nested Loop、Branch OR matching：V1 之后或显式 contract revision；
- backend runtime execution engine：不属于前端 M2.6。

## 12. Risk controls

| Risk | Control |
| --- | --- |
| schema validation 与 domain invariant 混为一谈 | schema 保证 shape/reference baseline；M2.6 validator 权威实现 mutation/readiness rules |
| 为允许草稿而放松 cycle/identity | structural hard gate + readiness diagnostics 双层模型 |
| command 失败后回滚不完整 | candidate-first pure function；失败从不提交 candidate |
| Branch config 和 edge 双事实漂移 | route target 只在 Edge；Case compound command 原子 reconciliation |
| Loop child mutation 污染 parent | explicit loop-body context + parent `applyLoopBodyCommand` boundary |
| 删除节点时猜测重连造成错误语义 | 只删除 incident edges，不自动 reconnect |
| UI/Canvas 再实现规则 | M2.7 只发 typed intent；domain error 是最终 authority |
| validator O(n²) | graph index + adjacency/reverse adjacency 单次构建；大图基准测试 |
| 随机测试 flaky | fixed seed、失败输出 seed/sequence、无 wall-clock/random global dependency |
| frozen contract 被隐式修改 | 默认不改 schemas；任何 persisted shape change 先走 contract review |

## 13. Pre-implementation review decisions

本计划建议在编码前视为冻结：

1. structural hard errors 与 readiness diagnostics 分层；
2. duplicate edge 使用 source + normalized handle + target；
3. remove node 同时删除 incident edges，但不自动重连；
4. remove edge 可以形成合法草稿，但 graph 不再 execution-ready；
5. Branch source 必须有 handle，且每个 handle 最多一条 outgoing edge；
6. Branch Case 删除与对应 edge 删除必须原子；
7. boundary nodes 不可删除/新增第二个；
8. minimal Agent/Loop factory 创建默认 boundary edge；
9. Loop body 是 owned embedded graph/layout，nested Loop 拒绝；
10. M2.6 不引入 Vue Flow UI，也不新增 backend API。

若 review 不修改以上决策，M2.6 可以按 Step 0 → Step 9 顺序直接实施。
