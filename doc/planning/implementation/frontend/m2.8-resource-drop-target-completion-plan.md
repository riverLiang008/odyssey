# M2.8 Resource Drop Target Completion Plan

> Status: Accepted for implementation
> Scope: Available Tool drag-and-drop into Agent Action Toolbox and Task sequence
> Visual reference: Figma `Research Agent — Workflow Canvas`
> Product reference: `doc/product/feature-specifications/resources/Update Agent Action Resource Configuration UI.md`

## 1. Outcome

Complete the missing Configure-mode resource interaction without weakening the existing Canvas boundaries:

1. a real `reusable-tool` payload can be dropped onto an Agent Action `Toolbox` zone;
2. a real `reusable-tool` payload can be dropped onto a Task sequence;
3. resource drops are never interpreted as Workflow-node creation;
4. root and Loop-child canvases use the same typed rules and preserve context isolation;
5. successful mutations persist through the existing Agent aggregate save path and survive refresh.

## 2. Frozen semantics

### 2.1 Agent Action Toolbox

- The drop target is the visible Toolbox region in the expanded Configure node.
- A successful drop appends the Tool ID to `AgentAction.config.reusableToolIds`.
- The reference is unique within one Agent Action; duplicate drops are rejected without mutation.
- The Tool must belong to the current Agent aggregate's `reusableTools` inventory.
- The node, Inspector and resource browser derive from the same canonical node config.

### 2.2 Task sequence

- A drop creates a new Task-owned `ToolStep`; it does not add an ID to an unordered reference set.
- The step is appended to the end of `Task.config.steps` in this increment. Array order remains execution order.
- Reusing the same reusable Tool in a Task is allowed because each drop creates an independently owned step ID.
- The new step copies the reusable Tool's kind and configuration, uses `fail_task` as the initial failure behavior, and preserves a schema-compatible output binding.
- The copied step is an independent Task-owned snapshot: it may be edited or left unchanged, does not receive later source updates, does not write changes back to the source, and remains valid if the source Reusable Tool is deleted.
- V1 does not persist a live source reference and therefore does not expose `Linked`, `Detach`, or `Update source` controls.
- If the reusable Tool cannot produce a valid `ToolStep` without additional required configuration, preflight returns a stable rejection and leaves the document unchanged. A future Tool configuration form may resolve that rejection; no invalid draft enters canonical state.
- Reordering and the complete Tool-step configuration form remain separate follow-up capabilities.

## 3. Interaction rules

- Resource targets are enabled only in Configure mode.
- `dragover` performs pure preflight and only highlights a compatible target.
- Invalid targets show the blocked cursor/icon and do not introduce a large red rectangle.
- A valid nested target consumes the drop so it cannot reach the Canvas pane or parent Loop/root canvas.
- Canvas-pane resource drops remain rejected and never create a Workflow node.
- Workflow-node-template payloads remain rejected by resource targets.
- Drag state is session-only and never enters WorkflowGraph, CanvasLayout or repository payloads.
- Click/keyboard equivalents remain available for Agent Action binding; Task keyboard insertion is exposed through the same typed action boundary even if its final picker UI is deferred.

## 4. Architecture

### 4.1 Typed targets and preflight

Extend `WorkflowResourceDropTarget` with a Task target:

```ts
{ kind: 'task-tool-sequence'; nodeId: UUID; insertionIndex: number }
```

`evaluateWorkflowResourceDrop` remains a pure function and returns either:

- `bind-reusable-tool` for Agent Action Toolbox;
- `append-task-tool-step` for Task;
- a stable invalid/duplicate/unavailable/unconfigurable error.

### 4.2 Domain commands

- Keep `bindAgentActionReusableTool` as the Agent Action mutation authority.
- Add a pure Task command that converts an available `AgentReusableTool` into a valid Task-owned `ToolStep`, then returns a new node config.
- The command must validate availability, target type, generated ID uniqueness, variable/output references and final schema shape before returning success.
- Root and Loop-child store actions only orchestrate the command and replace the correct aggregate once.

### 4.3 Components and Canvas adapter

- `WorkflowNodeRenderer` emits typed resource drag intents; it does not mutate node config.
- The expanded Toolbox and Task sequence become semantic drop zones with accessible labels.
- `WorkflowCanvas` supplies available-resource context, dispatches successful evaluations upward and preserves node/resource drag arbitration.
- Inline Loop delegates to the same contracts with its namespaced context.

## 5. Implementation sequence

1. Add domain conversion/append command and exhaustive tests.
2. Extend resource target/action unions and preflight cross-matrix tests.
3. Wire Agent Action Toolbox drop in expanded root and Loop-child nodes.
4. Wire Task sequence append drop in expanded root and Loop-child nodes.
5. Add valid/invalid/drag-over visual states without changing persisted layout.
6. Add component/integration tests for event consumption, duplicate behavior and context isolation.
7. Run lint, typecheck, tests and production build.
8. Verify with real Web API data: drop, save, refresh and revision progression.

## 6. Acceptance criteria

- Available Tool → Agent Action Toolbox succeeds in root and Loop child.
- Duplicate Toolbox drop is rejected atomically.
- Available Tool → Task appends exactly one valid step in root and Loop child.
- Repeating a Task drop creates a distinct step ID and preserves sequence order.
- Tool → Knowledge Space zone, resource → Canvas pane and Workflow node → resource zone are rejected without mutation.
- Nested valid drops are consumed exactly once.
- Successful operations increment local mutation sequence exactly once.
- Save and refresh preserve Toolbox references and Task steps.
- No session drag state is included in save input.
- Four frontend quality gates pass.
