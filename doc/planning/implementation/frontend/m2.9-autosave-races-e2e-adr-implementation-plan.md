# Odyssey M2.9 实施计划 — Autosave Races、E2E Hardening 与 M2 ADR

> Status: Proposed implementation plan  
> Milestone: M2.9 — final M2 closure  
> Depends on: M2.1–M2.8 accepted, current Journey/Agent revision-CAS Web API  
> Primary outcome: safe autosave under editing races, recoverable conflicts, repeatable vertical E2E, and an evidence-based M2 architecture decision

## 1. Outcome

M2.9 将当前“显式 Save + 基础 revision CAS”升级为可长期保留的编辑器持久化编排：

```text
typed domain mutation
        ↓
local mutation sequence
        ↓
debounced single-flight autosave
        ↓
immutable save snapshot + expected revision
        ↓
success / retryable failure / revision conflict
        ↓
safe follow-up save, explicit recovery, or navigation guard
```

完成后，用户应能连续编辑 Journey Pattern 和 Agent Workflow，而不会因为 debounce、保存中继续编辑、路由切换、旧响应或 revision conflict 丢失或静默覆盖数据。

M2.9 同时完成 M2 的最终 browser E2E、性能 smoke、completion report 与 ADR，作为进入 M3/M4/M5 的正式技术门禁。

## 4. Entry audit and blockers

编码前记录以下真实证据：

1. `PUT Journey` 与 `PUT Agent Workflow` 的 request/response schema；
2. 两者均要求 `expectedRevision`，成功返回新 revision 和 updated timestamp；
3. `409 REVISION_CONFLICT` 是否稳定返回 expected/current revision；
4. Journey 与 Agent load endpoint 可用于 conflict recovery；
5. Abort 后后端请求可能仍完成，因此前端必须同时具备 stale-result ignore；
6. 识别 Journey store 中两种 operation：
   - 仅修改本地 canonical document，必须进入 autosave；
   - 原子 Web command 已经保存并返回新 aggregate/revision，不得再次 autosave；
7. 准备两个独立浏览器/session 可制造真实 revision conflict；
8. 记录 M2.8 accepted aggregate IDs，验收数据删除前继续要求用户确认。

### 4.1 Backend blocker rule

若 conflict response 缺少 `currentRevision`，前端仍可通过 reload endpoint 获取最新 revision，但必须记录 contract degradation。若 load/save 本身不支持 revision CAS，则 M2.9 blocked，不允许用 last-write-wins 假装完成。

## 5. Persistence state model

废弃由 `saveStatus + error + counters` 任意组合表达状态的方式，建立 discriminated union：

```ts
type EditorPersistenceState =
  | {
      type: 'clean'
      serverRevision: number
      mutationSeq: number
      savedMutationSeq: number
    }
  | {
      type: 'dirty'
      serverRevision: number
      mutationSeq: number
      savedMutationSeq: number
      scheduledAt: number
    }
  | {
      type: 'saving'
      serverRevision: number
      mutationSeq: number
      savedMutationSeq: number
      requestSeq: number
      snapshotSeq: number
    }
  | {
      type: 'failed'
      serverRevision: number
      mutationSeq: number
      savedMutationSeq: number
      failedSnapshotSeq: number
      error: RepositoryError
    }
  | {
      type: 'conflict'
      localRevision: number
      serverRevision: number | null
      mutationSeq: number
      savedMutationSeq: number
      conflictedSnapshotSeq: number
      error: Extract<RepositoryError, { code: 'REVISION_CONFLICT' }>
    }
```

要求：

- 合法状态组合由类型保证；
- transition 由纯 reducer/state-machine function 完成；
- reducer 不读取 Vue、Pinia、router、timer 或 repository；
- document 与 session 仍不进入 persistence state；
- UI 文案通过 state type 映射，不从 counter/string 猜测；
- Journey 和 Workflow 共用状态语义，不复制两套不一致规则。

## 6. Autosave scheduling policy

### 6.1 Debounce

- 使用命名常量，初始值冻结为 `800ms`；
- mutation 发生后重置 debounce；
- manual `Save now` 取消 timer 并立即进入同一 save pipeline；
- invalid/rejected command 不调度保存；
- selection、panel、mode、focus、context、resource-browser state 不调度保存；
- node drag 只在 drag stop 后提交 layout mutation；
- viewport 高频事件先由 adapter/store 做合理节流，再进入 debounce，不能每帧请求 API。

### 6.2 Single-flight + coalescing

默认不并行发送同一 document 的两个保存请求：

1. saving 时继续编辑，只增加 `mutationSeq`；
2. 当前请求保存 immutable `snapshotSeq`；
3. 成功仅确认 `savedMutationSeq = snapshotSeq`；
4. 若 `mutationSeq > snapshotSeq`，使用新 server revision 立即排队一次 follow-up save；
5. 多个 saving-time edits 合并为一个最新 snapshot；
6. 不因较早 success 把仍有新修改的 UI 标成 Saved。

单飞策略从源头避免客户端自己制造 revision conflict；request sequence 仍用于 route/dispose、retry 和无法取消的迟到响应。

### 6.3 Snapshot ownership

- snapshot 在 request 启动前由 canonical document 深拷贝生成；
- response 只更新 revision/updatedAt 和 persistence state；
- response 不用旧 snapshot 替换当前 document；
- UI/session state 永不进入 snapshot；
- snapshot builder 继续通过 schema/runtime contract 验证。

## 7. Journey and Workflow mutation classification

### 7.1 Journey local-document mutations

以下操作成功后标记 dirty 并 autosave：

- assign/move/exchange/unassign Agent（仅本地 command 路径）；
- dynamic Slot add/remove/reorder；
-其他直接改变当前 Journey canonical pattern 的 typed command。

### 7.2 Server-authoritative Journey commands

以下操作已经通过原子 API 保存并返回 aggregate/revision，不得触发第二次 autosave：

- Guardrail add/remove；
- empty Slot `Open workflow` 原子 Agent 创建；
- occupied Slot removal；
- Agent Template instantiation；
-其他返回最新 Journey aggregate 的 lifecycle command。

执行 server-authoritative command 前：

1. 若存在 local dirty/saving，先 flush 并等待；
2. flush 失败或 conflict 时阻止 command；
3. command 使用最新 server revision；
4. 成功后以返回 aggregate 原子替换 document，并重置 autosave baseline；
5. 不允许 autosave 和 lifecycle command 使用同一 revision 并行写入。

### 7.3 Workflow mutations

所有已验收 graph/layout/config/resource application transaction 在成功后统一标记 dirty：

- root/Loop child node/edge create/remove/connect；
- root/child placement 与 viewport；
- Loop settings；
- Agent Action Tool/Knowledge Space bind/unbind；
-后续已进入 canonical save contract 的 variables/reusableTools 修改。

## 8. Failure and retry

### 8.1 Retryable failure

- NETWORK_FAILED、5xx normalization、temporary transport failure 进入 `failed`；
- 本地 document 保留；
- 不进行无限自动重试；
- UI 提供 `Retry now`；
- failure 后继续编辑：state 回到 dirty，并重新 debounce；
- retry 保存最新 document，而不是必然重放旧失败 snapshot；
-成功前不得显示 Saved。

### 8.2 Invalid response

`RESPONSE_INVALID` 视为非静默错误：保留本地 document、显示明确错误、允许重试，但必须在 telemetry/diagnostic 中与普通网络错误区分。

## 9. Revision-conflict recovery

Conflict 是阻塞 autosave 的显式状态，绝不自动覆盖服务器。

UI 至少提供：

1. **Stay and review**：保留当前本地 document，暂停 autosave；
2. **Reload server version**：明确确认将丢弃本地修改，重新 load 最新 aggregate；
3. **Overwrite with my local version**：明确说明会覆盖服务器较新配置；确认后先 load 最新 revision，再用保留的本地 canonical document 和该 revision 执行一次 CAS save。

规则：

- reload/overwrite 都是显式用户操作；
- overwrite 期间若再次 conflict，返回 conflict state，不循环强制覆盖；
- conflict dialog 不展示伪造 diff；
- V1 不做自动 merge；
- conflict 中允许用户查看/复制当前配置，但不得继续静默 autosave；
- destructive choice 的影响范围必须清楚；
- resolution 成功后重新建立 revision、saved sequence 与 document baseline。

## 10. Navigation and disposal

### 10.1 Internal route navigation

- clean：直接离开；
- dirty：立即 flush 并等待，成功后离开；
- saving：等待当前请求及必要 follow-up，成功后离开；
- failed/conflict：阻止导航并展示 `Stay` / `Leave without saving`；
- `Leave without saving` 必须明确确认；
- guard 不重复注册，不在多个页面散落实现。

### 10.2 Browser unload

- dirty/saving/failed/conflict 时注册 `beforeunload`；
- clean 时不注册；
- 浏览器 unload 不尝试用不支持 CAS 的 `sendBeacon` 保存；
- dispose 取消 timer、abort request、递增 request sequence，并忽略迟到响应；
-旧 route response 不得写入新 Agent/Journey store。

## 11. UI contract

统一展示状态：

| State | Toolbar status | Actions |
| --- | --- | --- |
| clean | Saved | Save disabled |
| dirty | Unsaved changes | Save now |
| saving | Saving… | Save disabled |
| failed | Save failed | Retry now |
| conflict | Conflict detected | Resolve conflict |

要求：

-状态使用 `role=status` / `role=alert`；
- manual Save、Retry、Resolve 支持键盘；
- conflict dialog 具备 focus management、Escape/close 语义；
- route guard dialog 与 conflict dialog 不同时打开；
- Focus Mode 中仍能看到保存状态和恢复入口；
-不使用 toast 作为唯一错误载体。

## 12. Implementation boundaries

建议新增：

```text
apps/web/src/domain/persistence/
  editorPersistenceState.ts       # pure transitions and invariants
  editorPersistenceState.test.ts

apps/web/src/stores/persistence/
  autosaveCoordinator.ts          # timer/request orchestration port
  autosaveCoordinator.test.ts

apps/web/src/features/editor-persistence/
  EditorSaveStatus.vue
  RevisionConflictDialog.vue
  UnsavedNavigationDialog.vue
```

Store 负责：

- canonical document snapshot；
- repository operation；
-应用 pure transition；
- document identity/revision check；
- lifecycle command coordination。

Component 只发出：

- `save-now`；
- `retry`；
- `resolve-conflict`；
- `confirm-leave`。

禁止：

- component 自建 timer 或调用 fetch；
- Journey/Workflow 各自复制一套 timer race 规则；
-旧 response 替换当前 document；
- conflict 时自动改 expectedRevision 重试；
-把 router、Vue Flow 或 DOM 类型放入 persistence domain。

## 13. Testing strategy

### 13.1 Pure state-machine tests

覆盖完整 transition table：

- clean → dirty → saving → clean；
-多次 dirty 合并；
- saving 中 edit → success → dirty/follow-up；
- failed → retry；
- failed 后 edit；
- conflict blocks schedule；
- stale success/failure ignored；
- overwrite 再 conflict；
- invariant：`savedMutationSeq <= snapshotSeq <= mutationSeq`（适用状态）。

推荐使用 fake timers 和 deferred promises，不依赖真实时间等待。

### 13.2 Store integration tests

Journey 与 Workflow 分别覆盖：

1. debounce 只发一次；
2. manual Save 复用同一 pipeline；
3. edit-during-save 产生一个 follow-up；
4. success 只更新 revision，不覆盖新 document；
5. route/dispose abort；
6. repository 忽略 abort 时仍忽略 stale result；
7. network failure/retry；
8. 409 conflict；
9. reload server；
10. explicit overwrite；
11. lifecycle command 先 flush，不与 autosave 并行；
12. session state 不进入 payload。

### 13.3 Component tests

-每个 persistence state 的文案和 actions；
- conflict confirmation；
- unsaved navigation confirmation；
- focus return；
- Escape 不误触 Canvas Delete；
- toolbar 在 Focus/Configure/Loop context 中保持一致。

### 13.4 Browser E2E

M2.9 应建立可重复运行的 browser E2E。若采用 Playwright：

-新增 `@playwright/test`、独立 config 和 `test:e2e` script；
-只使用正式 UI/API；
-测试数据通过正式 API setup，并记录 IDs；
- teardown 涉及真实删除时必须在受控测试 workspace 中执行；当前共享开发数据默认 retained；
-若 CI/本地浏览器依赖暂时无法冻结，不得用 jsdom 冒充 E2E，必须保留独立真实浏览器验收矩阵并记录 blocker。

核心路径：

```text
Journey List
→ open Journey
→ configure/move Slot
→ open Agent Workflow
→ mutate root and Loop child
→ bind/unbind resource
→ observe autosave
→ reload
→ verify equivalent aggregate
```

Race paths：

-连续三次 edit 最终只保存 latest；
- saving 时再次 edit；
-模拟延迟/失败；
-双 session 制造真实 conflict；
- route leave during dirty/saving；
-刷新/关闭页前的 native protection。

## 14. Performance and observability

记录但不泄漏业务内容：

- document type/id；
- mutationSeq、snapshotSeq、requestSeq；
- save transition；
- repository error code；
- debounce-to-save latency；
- graph validation duration。

Smoke gate：

-高频 node drag/viewport 事件不产生逐帧 API；
- 100-node graph 的合法 config/layout mutation 不产生明显主线程冻结；
- autosave 不深拷贝 Vue Flow VM 或 session；
- production bundle 增量有记录；
- console 无 warning/error/unhandled rejection。

Observability 首批可以使用可替换的 typed diagnostic sink；不得直接散落 `console.log`，不得记录 prompt、credentials、完整 Knowledge content 或 Tool secrets。

## 18. M2 ADR

新增 M2 architecture decision，至少回答：

- Vue Flow 是否保留，以及 adapter boundary；
- System Pattern Canvas 与 Agent Workflow Canvas 为何采用不同交互模型；
- canonical graph/layout/session 分离是否保留；
- Loop compound/nested ownership 如何演进；
- typed DnD arbitration 是否保留；
- repository/runtime validation/revision CAS 是否足够进入后续里程碑；
-哪些 fixture、placeholder、proof-only UI 应删除；
- M3（Behavior）、M4（Agent configuration）、M5（Variables/Tools/Knowledge resources）的稳定接入点；
-当前已知限制与后续 ADR 触发条件。

## 19. Risks and mitigations

| Risk | Mitigation |
| --- | --- |
| 每次 edit 并行 save 导致自冲突 | per-document single-flight + coalesced follow-up |
| success 覆盖 saving-time edits | revision-only response application；never replace current document |
| Journey atomic command 与 autosave争用 revision | mandatory flush barrier + returned aggregate baseline reset |
| failure 自动重试形成请求风暴 | no infinite retry；explicit Retry + edit-triggered debounce |
| conflict 自动覆盖他人修改 | blocked conflict state + explicit reload/overwrite confirmation |
| route leave 丢修改 | async internal guard + beforeunload fallback |
| abort 被当作绝对保证 | requestSeq/document identity stale check remains authoritative |
|两个 Store 演化出不同竞态语义 | shared pure state machine/coordinator contract |
| E2E 使用 mock 失去意义 | real API only；fixtures limited to unit/integration tests |
| M2.9 膨胀成资源或配置 CRUD | enforce explicit out-of-scope list |

## 20. Final handoff

M2.9 通过后：

- M2 Interaction Proof 正式完成；
-不再新增 M2.x feature batch；
-进入 M3/M4/M5 前以 ADR 的 retained boundaries 为准；
-任何新的复杂编辑器能力必须复用 autosave coordinator、revision CAS、route guard 和 canonical/session separation；
-真实验收数据继续 retained，除非用户明确授权清理。
