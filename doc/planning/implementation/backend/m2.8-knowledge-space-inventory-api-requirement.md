# M2.8 Knowledge Space Inventory API — Backend Requirement

> Status: Ready for backend implementation  
> Scope: M2.8 Workflow Editor resource inventory and persisted Knowledge Space references  
> Consumers: Odyssey Web Workflow Editor, root Workflow Canvas and Loop child Canvas  
> Related frontend plan: [`m2.8-modes-nested-loop-resource-dnd-implementation-plan.md`](../frontend/m2.8-modes-nested-loop-resource-dnd-implementation-plan.md)

## 1. Objective

M2.8 must let the Workflow Editor discover real Knowledge Spaces owned by the current Workspace and bind their IDs to `AgentActionNode.config.knowledgeSpaceIds`.

The frontend must not use fixtures, seed-only constants, direct database access, or an in-memory fallback. The backend must provide:

1. one Workspace-scoped Knowledge Space summary list endpoint;
2. complete validation of Knowledge Space references during the existing Agent Workflow aggregate save;
3. atomic synchronization of `agent_workflow_knowledge_space_reference` with the saved aggregate.

Full Knowledge Space CRUD, document browsing, graph editing, indexing operations, and archive management are not part of this requirement.

## 2. Frozen API surface

### 2.1 List inventory

```http
GET /api/v1/knowledge-spaces?query={query}&page={page}&pageSize={pageSize}
```

OpenAPI identity:

```text
operationId: listKnowledgeSpaces
tag: knowledge-spaces
```

Query contract:

| Parameter | Type | Default | Rules |
| --- | --- | --- | --- |
| `query` | string | `""` | trim; maximum 200 characters; case-insensitive search over `name` and non-null `description`; literal `%`/`_` must be escaped |
| `page` | integer | `1` | minimum 1 |
| `pageSize` | integer | `20` | minimum 1; maximum 100 |

Unknown query parameters must be rejected if the project boundary infrastructure supports strict query DTOs. Invalid input returns the standard `422 VALIDATION_FAILED` envelope.

Stable ordering is mandatory:

```text
updated_at DESC, id ASC
```

Search, ordering, total count, and pagination must be evaluated inside the same Current Workspace scope. `total` is the number of matched records before page slicing.

### 2.2 Canonical response

```json
{
  "items": [
    {
      "id": "0195f076-b6e6-7ef0-98db-d721990f8998",
      "name": "Product Research",
      "description": "Reviewed product and market documents.",
      "knowledgeSpaceCategoryId": "0195f076-b6e6-7ef0-98db-d721990f8999",
      "lifecycleStatus": "ready",
      "graphStatus": "healthy",
      "updatedAt": "2026-08-26T12:00:00.000Z"
    }
  ],
  "page": 1,
  "pageSize": 20,
  "total": 1
}
```

Strict DTO definitions:

```text
KnowledgeSpaceLifecycleStatus = initializing | ready | syncing | failed
KnowledgeGraphStatus = not_indexed | healthy | needs_review | error

KnowledgeSpaceSummary
  id: UUID
  name: trimmed string, 1..255
  description: string | null
  knowledgeSpaceCategoryId: UUID
  lifecycleStatus: KnowledgeSpaceLifecycleStatus
  graphStatus: KnowledgeGraphStatus
  updatedAt: canonical UTC timestamp

KnowledgeSpaceSummaryPage
  items: KnowledgeSpaceSummary[]
  page: positive integer
  pageSize: integer 1..100
  total: non-negative integer
```

The lowercase status values above match the accepted database contract and are frozen for this endpoint. Do not expose the uppercase values from the older product draft without a repository-wide contract migration.

Do not include:

- `workspaceId`;
- normalized names or internal storage columns;
- ORM objects;
- full Knowledge documents, graph data, issue details, signed URLs, or secrets;
- presentation strings such as “Ready to use”;
- invented counts or fields that cannot be derived reliably.

### 2.3 HTTP results

| Condition | Status | Contract |
| --- | --- | --- |
| Valid request, items exist | `200` | canonical page |
| Valid request, no matches | `200` | `items: []`, `total: 0`, requested `page/pageSize` |
| Invalid query/page/pageSize | `422` | standard `VALIDATION_FAILED` envelope |
| Current Workspace unavailable | `503` | standard `CURRENT_WORKSPACE_UNAVAILABLE` envelope |
| Unexpected failure | `500` | generic project error response; no SQL or stack leakage |

This list endpoint is read-only and has no revision/`If-Match` requirement. M2.8 does not require ETag, cursor pagination, or a detail endpoint.

## 3. Workspace ownership and visibility

- Current Workspace comes exclusively from `get_current_workspace` or the equivalent server dependency.
- The client must not send `workspaceId` in path, query, headers, or body.
- Repository SQL must include `knowledge_space.workspace_id = :current_workspace_id`.
- No unscoped `get_by_id` followed by a Python ownership check is acceptable.
- Rows from another Workspace never appear in `items` or contribute to `total`.
- Ordering must not rely on database natural order.

M2.8 lists every non-deleted Knowledge Space represented by the current schema. Lifecycle and graph statuses are returned so the frontend can disable resources that are not usable. This requirement does not add an archive field or silently infer archived state.

Frontend selection policy for this milestone:

- selectable: `lifecycleStatus in {ready, syncing}` and `graphStatus in {healthy, needs_review}`;
- visible but disabled: all other returned combinations.

The backend must return facts, not a presentation-only `isSelectable` flag.

## 4. Existing Agent Workflow save protocol

No separate HTTP bind/unbind endpoint is required. Binding remains part of the existing aggregate save:

```http
PUT /api/v1/journeys/{journeyId}/agents/{agentId}
Content-Type: application/json
```

The existing strict `SaveAgentWorkflowRequest` and `expectedRevision` CAS behavior remain authoritative. Knowledge Space IDs may occur in:

1. root and Loop-child `agent_action.config.knowledgeSpaceIds`;
2. Agent `reusableTools` whose kind is `knowledge_retrieval`;
3. root and Loop-child Task steps whose kind is `knowledge_retrieval`.

Before writing the candidate aggregate, the application service must:

1. parse and validate the full canonical request;
2. recursively extract every Knowledge Space reference with its owner kind, owner ID, and issue path;
3. query all distinct referenced IDs inside the Current Workspace scope;
4. reject the complete save if any ID is missing or belongs to another Workspace;
5. execute the existing Agent Workflow database-level revision CAS;
6. replace/synchronize the derived reference rows;
7. validate and return the complete canonical Agent Workflow aggregate;
8. commit once.

Missing and cross-Workspace references must both return:

```http
404 NOT_FOUND
```

```json
{
  "error": {
    "code": "NOT_FOUND",
    "details": {}
  }
}
```

This deliberately hides whether the supplied ID exists in another Workspace. Validation rejection, conflict, or rollback must not increment Agent revision or alter reference rows.

## 5. Derived reference-table synchronization

`agent_workflow_knowledge_space_reference` is a derived index of the canonical Agent aggregate, not a second source of truth.

For every extracted reference create exactly one logical row:

| JSON owner | `owner_kind` | `owner_id` |
| --- | --- | --- |
| Agent Action node | `agent_action` | node UUID |
| Agent reusable Tool | `reusable_tool` | reusable Tool UUID |
| Task knowledge-retrieval step | `task_tool` | step UUID |

Required invariant:

```text
UNIQUE(agent_workflow_id, knowledge_space_id, owner_kind, owner_id)
```

Synchronization rules:

- compute the complete desired set from the candidate request;
- insert missing rows and remove stale rows inside the same transaction as Workflow JSON and revision CAS;
- duplicate IDs within one Agent Action remain invalid under the canonical schema;
- repeated references owned by different nodes/tools produce distinct rows;
- repository methods may `execute/flush`, never `commit`;
- failure injection between aggregate update and reference synchronization must prove full rollback using a separate session.

Existing FK `ON DELETE RESTRICT` behavior must remain. A referenced Knowledge Space cannot be deleted through a future CRUD endpoint without an explicit product transition; M2.8 adds no delete endpoint.

## 6. Architecture and implementation boundaries

Suggested feature package:

```text
apps/api/src/odyssey_api/knowledge/
  dto.py
  repository.py
  service.py
  router.py
```

Responsibilities:

- router: query boundary, dependencies, response declaration only;
- DTO: strict query/response models and camelCase aliases;
- service: use-case orchestration and response validation;
- repository: stable Workspace-scoped list/count statements;
- Journey workflow service/domain: recursive reference extraction, ownership validation, and transactional reference synchronization.

Register the Knowledge Space router in `main.py` under the existing `/api/v1` prefix. Do not create a generic CRUD repository or return `KnowledgeSpace` ORM rows directly.

The existing initial migration already contains the Knowledge Space and Agent Workflow reference tables and relevant indexes. A new migration is not expected unless implementation demonstrates a real schema mismatch. If one is required, document why the accepted schema cannot satisfy this contract.

## 7. Shared TypeScript contract handoff

Add strict runtime schemas and exported types under `packages/schemas` for:

```text
knowledgeSpaceLifecycleStatusSchema
knowledgeGraphStatusSchema
knowledgeSpaceSummarySchema
knowledgeSpaceSummaryPageSchema
```

The backend Pydantic DTO and TypeScript Zod schema must have parity fixtures covering:

- a populated page;
- empty page;
- every lifecycle/graph enum value;
- nullable description;
- extra-field rejection;
- invalid UUID/timestamp/page values.

After the backend is ready, the frontend repository will add:

```ts
listKnowledgeSpaces(input, options): Promise<RepositoryResult<KnowledgeSpaceSummaryPage>>
```

and runtime-validate every response. Do not make the frontend parse ORM casing or legacy uppercase enum values.

## 8. Required tests

### Contract and HTTP

- OpenAPI contains `GET /api/v1/knowledge-spaces` with `operationId=listKnowledgeSpaces`.
- Defaults, limits, camelCase response, canonical timestamps, and strict validation are tested.
- Empty and populated pages are tested.
- Search matches name and description case-insensitively and escapes wildcard characters.
- Ordering uses `updated_at DESC, id ASC`, including identical timestamps.
- `total` is scoped and calculated before pagination.
- Current Workspace unavailable returns the existing `503` envelope.

### Workspace isolation

- two Workspaces with overlapping search terms return only their own rows and counts;
- a cross-Workspace Knowledge Space reference in Workflow save returns indistinguishable `404 NOT_FOUND`;
- logs and error details do not reveal the foreign Knowledge Space.

### PostgreSQL transaction and concurrency

- successful Workflow save updates JSON, derived reference rows, revision, and response together;
- removing a binding removes the stale derived row;
- root and Loop-child references are both indexed;
- reusable Tool and Task-step references use the correct owner kind/ID;
- injected failure after CAS but before/during reference synchronization rolls everything back;
- two independent sessions saving the same revision produce one success and one `409 REVISION_CONFLICT`;
- rejected save does not consume revision;
- tests use PostgreSQL, not SQLite, for JSONB/CAS/transaction proof.

### Quality gates

```bash
cd apps/api
uv run ruff check .
uv run pytest
```

If `packages/schemas` changes, also run the applicable workspace lint, typecheck, tests, and build.

## 9. Acceptance criteria

The backend handoff is complete only when:

- the endpoint is visible in `/docs` and returns real current-Workspace records;
- frontend can distinguish loading, empty, populated, validation failure, network failure, and unavailable Workspace without fixtures;
- pagination and search are deterministic;
- cross-Workspace records never appear or contribute to totals;
- Agent Workflow save validates all root/nested Knowledge Space references;
- the canonical aggregate and derived reference table remain transactionally consistent;
- revision semantics remain unchanged and CAS-safe;
- no unrelated Knowledge Space CRUD endpoints were added;
- OpenAPI, Pydantic, Zod, parity fixtures, PostgreSQL integration tests, Ruff, and pytest all pass.

## 10. Explicit non-goals

- Knowledge Space create/update/delete/detail endpoints;
- document/folder/tag/relation/issue APIs;
- indexing, retry, Steward, Curator, or object-storage operations;
- Tool Template/Definition inventory APIs;
- community marketplace, favorite, category management, or archive workflow;
- a per-drop mutation API;
- server persistence of editor selection, mode, Focus, drag state, or Vue Flow data.
